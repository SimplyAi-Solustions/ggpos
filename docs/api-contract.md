# GG Vault custom API contract (Phase 2)

The counter app talks to PocketBase's collection API for reads, drafts and simple writes, and to these custom routes for anything that must be transactional, gated or audited. The routes live in `pb/pb_hooks/` and are mounted under `/api/vault/`. Backend and frontend packages are built against this document in parallel; change it here first when a shape has to change.

Conventions
- Every route requires a `staff` token in `Authorization`. Routes marked **admin** require `role = "admin"`. Routes marked **step-up** also require the `X-Step-Up` header (see step-up below).
- Money is an integer of GBP pence everywhere. Dates and timestamps are ISO 8601 strings in UTC.
- Errors use PocketBase's shape: `{ "code": 400, "message": "...", "data": { "field": { "message": "..." } } }`. Codes: 400 validation, 401 no auth, 403 wrong role or missing step-up, 404 not found, 409 state conflict (already sold, session already open), 422 business rule refused (ID gate, cash cap, under 18). The `message` is written for staff to read on screen and says what to do next.
- Every route writes one `audit_log` row (identifiers and changed field names only, never values from customers, customer_private, id_documents, staff or settings).

## Step-up

`POST /api/vault/step-up` with `{ "password": "..." }` re-checks the signed-in staff member's password and returns `{ "token": "<jwt>", "expires_at": "..." }`, valid for 10 minutes, signed with `$security.createJWT`. Sensitive routes verify it with `$security.parseJWT` and refuse with 403 and the message "Confirm your password to continue." when it is missing or expired.

## First sign-in

Not a custom route: the forced password change runs on the collection API, and is recorded here because it is the first thing any staff token ever does.

`staff.must_change_password` (bool, `1789820760_staff_must_change_password.js`) is true on an account still using a password somebody else chose, which is what the seeded first admin's is. It rides back on the record `POST /api/collections/staff/auth-with-password` returns, so the counter knows to lock without a second call, and while it is true every route in the app redirects to `/counter/password` and the shell draws no nav, palette, scan listener or idle lock.

**The lock is the server's, not the screen's.** A `routerUse` middleware in `pb_hooks/staff.pb.js` refuses every request made with a staff token whose record still carries the flag, with 403 and "Set a new password before doing anything else.", on any device and through any client. Exactly three calls are allowed:

- `POST /api/collections/staff/auth-refresh`, so the session does not die while the form is being filled in;
- `PATCH /api/collections/staff/records/:id` against the caller's **own** id, which is the change itself;
- `GET /api/health`, which answers the same to everyone and must not depend on who is signed in.

Superusers, `customers` tokens and requests with no usable token are untouched, so signing in still works: a locked account can always reach the one screen that lets it out, and nothing else.

The change itself is PocketBase's own record update: `PATCH /api/collections/staff/records/:id` with `{ "oldPassword": "...", "password": "...", "passwordConfirm": "..." }` against the caller's own id. `pb_hooks/staff.pb.js` adds three rules to it:

- a new password under 12 characters, or equal to the one already on the account, is refused with 400 and "Choose a password of at least 12 characters, and not the one you are using now." (PocketBase's own minimum is 8);
- `must_change_password` is put back to its stored value whenever the caller is writing their own row, whatever their role, and whenever the caller is not an admin at all, so no account unlocks itself by sending the field. A superuser, and an admin acting on somebody else's row, may still set and clear it;
- on success the flag is cleared in the same save and one `audit_log` row is written: `staff_password_changed` when the owner changed their own password, `staff_password_set` when anybody else set it, `staff_lock_changed` when the flag moved without a password change. `meta` is `{ fields, record, by }` - the changed field names, the staff id and who did it ("superuser", or the caller's own staff id for an admin). No password is ever read into the row, the response or the log, and `staff` is not in `audit.pb.js`'s update list, so one change is one row.

A successful change rotates the account's token key, so every existing token dies with it: the counter signs in again with the new password itself and carries on with the record that comes back. `staff`'s API rules are admin-only throughout, so only a staff member with `role = "admin"` can make this call at all; a plain staff member's password is set by a superuser from `/_/`, where PocketBase's own 8-character floor applies rather than this 12-character rule.

## Trade-ins

Drafts and lines are created and edited through the collection API (`trade_ins` with `status = "draft"`, `trade_in_lines`, batch for multi-line edits). Completion is the custom route.

`POST /api/vault/trade-ins/:id/complete`

Request
```json
{
  "payout_type": "cash" | "credit" | "mixed",
  "payout_cash": 0,
  "payout_credit": 0,
  "terms_accepted": true,
  "signature": "data:image/png;base64,...",
  "cash_session": "<id or null>",
  "id_check": null | {
    "id_type": "passport" | "driving_licence" | "other",
    "id_expiry": "2028-06-30",
    "id_ref_last4": "1234",
    "dob": "1990-01-31",
    "address": "1 High Street, Bolsover, S44 6AA",
    "id_document": "<id_documents id from the id-check route, or null>"
  }
}
```

Server checks, in order: the trade-in belongs to a customer and is `draft`, `offered` or `accepted` with at least one accepted line; `payout_cash + payout_credit` equals the sum of accepted `offer_price × qty`; when `payout_cash > 0`: an open cash session is supplied and matches, `payout_cash <= settings.cash_cap`, the customer's `customer_private.address` is present (or supplied in `id_check`), `id_status = "verified"` with an unexpired `id_expiry` (or a full `id_check` is supplied in the same call, which sets it), the customer is 18 or over when `dob` is known; `terms_accepted` is true.

Inside one transaction: assign `number` from `counters.trade_in` (`GG-BI-000123`), write the seller snapshot onto the trade-in, create `items` for every accepted line (one row per unit for single, graded and retro with `qty = 1`; one row with `qty` for sealed and accessory), each with `status = "in_stock"`, `cost = offer_price`, `market_at_intake = market_price`, `source = "trade_in"`, `trade_in_line` set, `acquired_at = now`, `tax_scheme = "margin"`; link each line's `item`; write `credit_ledger` (`+payout_credit`, reason `trade_in`) and recompute `customer_private.credit_balance`; write `cash_movements` (type `payout`, amount `payout_cash`) against the session; write `points_ledger` for the credit portion using the shared loyalty evaluator; create one `label_jobs` row per item using the template for its kind; set `status = "completed"`, `completed_at`, `staff`, `signature`; audit.

Response 200
```json
{
  "trade_in": { "id": "...", "number": "GG-BI-000123", "status": "completed", "payout_cash": 0, "payout_credit": 0 },
  "items": [ { "id": "...", "sku": "GGS7F3K2Q", "title": "Charizard ex #199" } ],
  "labels_queued": 3,
  "points_earned": 150,
  "credit_balance": 4500
}
```

## ID check

`POST /api/vault/customers/:id/id-check` (multipart form) with fields `photo` (image file, already downscaled by the client), `id_type`, `id_expiry`, `id_ref_last4`, `dob`, `address`.

Server: reads the photo bytes, encrypts them with `$security.encrypt` and the `GG_ID_PHOTO_KEY` environment variable (refuses with 500 "ID photo key is not configured" when the variable is missing), stores the ciphertext as the `photo` file on a new `id_documents` row with `taken_by`, `taken_at`, `expires_at = now + settings.id_photo_retention_months`; updates `customer_private` (`id_status = "verified"`, `id_type`, `id_expiry`, `id_ref_last4`, `dob`, `address`, `id_verified_by`, `id_verified_at`); audit.

The MIME type is sniffed from the file's first bytes (JPEG, PNG, WebP, HEIC/HEIF); a `mime` form field is ignored. Anything else is 400 "That file is not a photo. Take a JPEG or PNG photo of the ID." The upload is capped at 8 MB: 400 "That photo is over 8 MB. Take it again at a lower resolution."

Response 200: `{ "id_document": "<id>", "id_status": "verified", "id_expiry": "2028-06-30", "expires_at": "2027-09-20T..." }`.

`GET /api/vault/id-photo/:id` (**admin**, **step-up**): writes the audit row first, decrypts, and streams the image with `Content-Type` from the stored MIME, `Cache-Control: no-store`, `Content-Disposition: inline`. 404 when purged.

`GET /api/vault/customers/:id/id-document` (staff): the newest `id_documents` row for that customer whose photo file is still on disk, so the buy-in screen can tell whether the ID gate will pass without being able to read `id_documents` itself (its API rules are all null). Never returns the photo or anything else off the row.

Response 200: `{ "document": { "id": "...", "taken_at": "...", "expires_at": "...", "taken_by": "<staff id>" } | null }`. 404 when the customer does not exist.

## Sales

`POST /api/vault/sales/complete`

Request
```json
{
  "lines": [ { "item": "<id>", "qty": 1, "unit_price": 32499, "discount": 0 } ],
  "customer": "<id or null>",
  "payment": "sumup_card" | "cash" | "store_credit" | "points" | "mixed",
  "payment_split": { "sumup_card": 0, "cash": 0, "store_credit": 0, "points": 0 },
  "discount": 0,
  "discount_source": "manual" | "tier_perk" | "reward" | null,
  "reward_code": "GGV...." | null,
  "cash_session": "<id or null>",
  "sumup_ref": "",
  "client_id": "<optional, up to 64 characters>"
}
```

Server checks: every item is `in_stock` (or `reserved` for this customer) with enough `qty`; `payment_split` sums to the total after discount (for a single payment method the split may be omitted); cash requires an open session; store credit requires balance; points pass `checkPointsRedemption` from the shared evaluator; a reward code must be an unused, unexpired `reward_redemptions` row for this customer.

`client_id` is the offline queue's idempotency key: the counter PWA generates one per sale before it ever leaves the device, so a queued "mark sold" that gets replayed after a reconnect (docs/PLAN.md, "Offline") cannot create the sale twice. When `client_id` is given and a `sales` row already carries it, the server skips every check above and returns 200 with the same body the original completion produced, rebuilt from that stored sale (`number`, `total`, `status`, `points_earned`) and the customer's **current** balances, rather than creating a second sale. `sales.client_id` carries a unique index where non-empty, so this holds even under a genuine race. 400 when `client_id` is over 64 characters.

Inside one transaction: assign `number` from `counters.sale` (`GG-S-000456`); set singles to `sold`, decrement multi-quantity lines and set `sold` at zero; write `sale_lines` with `vat_rate` and `tax_scheme` from the item; write `credit_ledger` (`-store_credit`, reason `sale`); write `points_ledger` (`-points`, reason `redeem`) and then the points earned (`earn_sale`, computed with the shared `evaluateSalePoints` over live `loyalty_rules` and the customer's tier); mark the reward redemption `used`; write `cash_movements` (type `cash_sale`); recompute cached balances; audit any `unit_price` that differs from `items.price` as a price override.

Response 200
```json
{
  "sale": { "id": "...", "number": "GG-S-000456", "total": 32499, "status": "complete" },
  "sumup_amount": 32499,
  "points_earned": 325,
  "credit_balance": 0,
  "points_balance": 1240
}
```

A `reward_code` needs a customer on the sale and must belong to them; `discount_source` must be `"reward"`; the reward's type must be `money_off` and `discount` must equal its value in pence. Each of those is a 422.

`POST /api/vault/sales/:id/refund` (**step-up**)

Request: `{ "lines": [ { "sale_line": "<id>", "qty": 1 } ], "reason": "...", "refund_method": "cash" | "store_credit" | "sumup_card" }`.

Server, in one transaction: items back to `in_stock` (or `qty` incremented), `sale_lines.refunded_qty` moved up and `status = "refunded"` once it reaches `qty`, `sales.refunded_total` moved up and `sales.status` set to `refunded` or `part_refunded`, reversing `credit_ledger` and `cash_movements` rows, a `points_ledger` row with reason `refund_reverse` for the points that sale earned on those units, the reason saved as a `notes` row against the sale, audit.

Amounts come from the as-sold figures, cumulatively, so any sequence of partial refunds adds back up to exactly what was charged. 409 when the line is already refunded, when fewer units are still sold than asked for, or when the item has since been deleted.

Response 200: `{ "sale": { "id": "...", "status": "part_refunded" }, "refunded": 32499, "refunded_total": 32499, "points_reversed": 325, "credit_balance": 0, "points_balance": 915 }`.

## Cash sessions

- `POST /api/vault/cash-sessions/open` with `{ "float": 10000 }`: 409 when a session is already open. Returns the session.
- `GET /api/vault/cash-sessions/current`: `{ "session": {...} | null, "expected": 0, "movements": [...] }`. `cash_movements.amount` is signed (cash sales and float_in positive; payouts, refunds and bank drops negative; adjustments carry their own sign), so `expected = float + sum(amount)`. `open` returns the same `{ session, expected, movements }` shape.
- `POST /api/vault/cash-sessions/:id/close` with `{ "counted": 12345, "notes": "" }`: sets `expected`, `counted`, `variance = counted - expected`, `closed_by`, `closed_at`; a variance over `settings.cash_variance_alert` (pence) is audited. Returns the closed session.

## Stock counts

Counts and their lines are ordinary `stock_counts` / `stock_count_lines` rows (staff create and update rules); closing is the one custom route, because it has to reconcile every line, optionally move stock and audit in a single transaction, and because `status` must never reach `"closed"` any other way.

`POST /api/vault/stock-counts/:id/close` (**admin**) with `{ "move_unexpected": true | false }`.

In one transaction: for every `stock_count_lines` row on the count, `variance = scanned_qty - expected_qty`; when `move_unexpected` is true, every line whose item was scanned but not expected (`expected_qty = 0` and `scanned_qty > 0`) has its item's `location` set to the count's own `location`; the count's `status` becomes `closed`, with `closed_by` and `closed_at`. Audit carries the count id, the number of lines and the ids of any items moved.

Response 200: `{ "stock_count": { "id": "...", "status": "closed", "closed_by": "...", "closed_at": "..." }, "lines": 12, "moved_items": [ "..." ] }`. 404 when the count does not exist, 409 when it is already closed, 403 for a non-admin staff member.

`stock_counts.status` cannot be set to any value through the collection API (`updateRule` requires `@request.body.status:isset = false`), so this route is the only way a count closes; a plain staff token may still create a count, add lines to it, and edit its `location` or `notes`.

**Only one count may be open per location at a time**, enforced by a partial unique index (`stock_counts (location) WHERE status = 'open'`) - creating a second `open` count against a location that already has one is refused with 409 `"A count of this location is already open. Carry on with it or close it first."`, through `onRecordCreateRequest` on the plain collection-API create, not a custom route. The client already offers to resume an open count rather than start a second one; this is what makes that rule real rather than merely a UI convention.

## Labels

Label jobs are ordinary `label_jobs` rows (staff create rule). The print page is client-side: `/labels/print?jobs=<id>,<id>` renders one label per page with `@page` sized from the job's template and marks each job `printed` after `window.print()` resolves. No custom route.

## Receipts

- `GET /api/vault/trade-ins/:id/receipt`: JSON with everything the receipt page needs (shop details from `settings`, seller snapshot, lines with titles and offers, payout, signature URL through a short-lived file token, terms text). The app renders it at `/counter/trade/:id/receipt` for A4 print.
- `POST /api/vault/trade-ins/:id/receipt/email`: sends the receipt to the customer's email through `$mails` with the provider configured in `settings`; `{ "sent": true }` or 422 "This customer has no email on file."

## Exports

`GET /api/vault/exports/stock-book?from=YYYY-MM-DD&to=YYYY-MM-DD` (**admin**): CSV of margin scheme items acquired in the range with the columns in `docs/csv-formats.md` (stock number, purchase date and ref, seller name and address, description, cost, sale date and ref, sale price, margin). `Content-Disposition: attachment`.

## Config

`GET /api/vault/config` (staff): the read-only window onto the admin-only reference collections, so an ordinary staff member at the counter can price an item, see the cash variance threshold and show a customer their tier.

Response 200
```json
{
  "settings": { "cash_cap": 800000, "offer": { "bulkThreshold": 100, "...": 0 }, "...": "" },
  "pricing_rules": [ { "id": "...", "kind": "single", "band_min": 0, "...": 0 } ],
  "loyalty": {
    "programme": { "id": "...", "enabled": true, "...": 0 },
    "rules": [ { "id": "...", "type": "multiplier", "...": 0 } ],
    "tiers": [ { "id": "...", "name": "Member", "...": 0 } ]
  }
}
```

`settings` is every field of the settings record except `api_keys`, `email` and anything whose name contains "key" or "secret", so the third-party API keys, the mail key and the VAPID keys never leave the server. `pricing_rules` and `loyalty.rules` are the active rows, highest priority first (the order the evaluators break ties in); `loyalty.tiers` is every tier by `sort`. 401 without a staff token. No audit row: every counter screen loads this.

## Customer records

`POST /api/vault/customers/:id/merge` (**step-up**) with `{ "into": "<id>" }`, where `:id` is the duplicate to fold in and `into` is the record to keep.

In one transaction every relation is re-pointed at the record being kept (`trade_ins`, `sales`, `credit_ledger`, `points_ledger`, `quotes`, `want_list`, `notifications`, `push_subscriptions`, `reward_redemptions`, `referrals` at both ends, `memberships`, `id_documents`, `items.reserved_for`, `customers.referred_by`, and `notes` rows targeting the duplicate). `perk_usage` is the one exception: it carries a unique index on `(customer, perk_type, period)`, so a row that clashes with one the kept record already has is added into it by `used_count` and then deleted, and a row with no counterpart is re-pointed as normal. On `customer_private`, fields that are empty on the record being kept are filled from the duplicate (address, date of birth), flags are unioned, notes are appended on a new line, and the ID fields move over only when the record being kept has no verified ID and the duplicate has one. Both cached balances are then recomputed from the ledgers, and the duplicate's `customer_private` and `customers` rows are deleted.

Response 200: `{ "customer": { ...the kept record... }, "moved": { "trade_ins": 2, "credit_ledger": 5 } }`. 400 with no `into`, 409 when the two ids are the same, 404 when either is missing. Audit carries the two ids and the counts.

`POST /api/vault/customers/:id/erase` (**admin**, **step-up**), no body. The UK GDPR Article 17 erasure.

422 when the customer still holds store credit: "This customer still has £15.00 store credit. Pay it out or write it off first."

In one transaction: `customers` keeps its `code` and gets `name = "Erased customer"`, an empty email and phone, `marketing_consent = false`, no birthday month and a fresh `qr_token`; `customer_private` has its address, date of birth, notes, flags and every ID field cleared and `id_status = "none"`; the customer's `id_documents` rows are deleted with their files; open (`issued`) `reward_redemptions` become `cancelled`; their `want_list`, `notifications`, `push_subscriptions` and `quotes` rows are deleted, quote photos included. Trade-ins, sales and both ledgers stay untouched, seller snapshot and all: Article 17(3)(b) keeps the record the shop is required by law to hold.

Response 200: `{ "erased": true, "customer": { ...the anonymised record... } }`. Audit carries the customer id and the counts.

## Phase 4: stats and reports

`daily_stats`, the nine reports of docs/PLAN.md's "Reporting" table, saved and scheduled reports, and the Monday admin digest. Conventions are as above: a `staff` token on every route, money as integer GBP pence, dates as ISO `YYYY-MM-DD`. Every route in this section writes one `audit_log` row where noted; the plain report reads (`GET /api/vault/reports/*`) do not, matching `GET /api/vault/config`'s own reasoning - an ordinary staff member's report view is not sensitive and would bury the rows that matter.

### daily_stats

One row per UTC calendar day, built straight from the ledgers and rows - never from a cached balance (CLAUDE.md's "Pricing" section states this rule for offers; it applies here to every figure). Every date bound in this package is a UTC day, compared in PocketBase's own stored form (`YYYY-MM-DD HH:MM:SS.sssZ`, a space rather than a "T" - `pb_hooks/crons.pb.js`'s existing `pbDate()` and `exports.pb.js`'s `acquired_at` range do the same for the same reason). **Every sales figure below groups, filters and ranges on `sales.occurred_at`, never `sales.created`** - `occurred_at` is the sale's own date (backfilled to `created` for rows from before the field existed, set to now by a hook for an ordinary counter sale, set to the order's own date by the eBay orders import), where `created` is only ever when the database row was written; an eBay orders file imported on a Friday covering a week of orders must book each sale on its own day, not on the Friday the import ran. `sale_lines` has no `occurred_at` of its own, so every `sale_lines` query in this package reaches it through the relation (`sale.occurred_at`). Refund figures (`items_out`'s net-of-refunds, a refund's own effect on `credit_ledger` / `points_ledger` / `cash_movements`) keep the dates they already used - a refund has no `occurred_at` of its own to move to.

- `sales_count` / `sales_total_by_payment`: every `sales` row with `occurred_at` that day, counted and summed by `payment`: `sumup_card`, `cash`, `store_credit`, `points`, `mixed`, and **`none`** - an eBay order import (`sales.channel = "ebay"`, `docs/api-contract.md`'s "Phase 4: exports, imports and SumUp") leaves `payment` blank because eBay took the money, and that is its own bucket, never folded into `mixed` (which means the shop itself split one sale across methods). `sales_count` counts every sale regardless of channel or payment, eBay imports included. **This stays gross** - what was actually taken by each payment method that day - never net of the refunds below.
- `sales_refunded`: the sum of `sales.refunded_total` for every sale with `occurred_at` that day, whichever day the refund itself was actually processed on - the same "belongs to the day the sale occurred" rule `items_out` already follows. This is the one field every revenue figure in this package (every report's `totals.revenue` and `series` values, the digest, a scheduled report's emailed totals) subtracts from the gross above to arrive at **net of refunds**; `sales_total_by_payment` itself is never adjusted. A sale refunded weeks after it happened moves this day's `sales_refunded` (and so every net revenue figure that reads it) the next time this row is rebuilt, not before.
- `buy_in_count` / `buy_in_total_by_payout`: every `trade_ins` row with `status = "completed"` and `completed_at` that day, counted, and its `payout_cash` / `payout_credit` summed into `{ cash, credit }` - two buckets, not three: a `payout_type: "mixed"` trade-in's cash and credit portions land in the matching bucket directly, since `payout_cash` and `payout_credit` are already split on the row.
- `items_in`: `items` rows with `acquired_at` that day (every source: trade-in, supplier, opening stock).
- `items_out`: `sale_lines` rows whose sale has `occurred_at` that day, summed as `qty - refunded_qty` (only where positive) - net of every refund on file at build time, not only refunds that happened the same day. Rebuilding an old day's row therefore nets off a later refund against the day the sale occurred, which is the point of "net of refunds".
- `stock_value_cost` / `stock_value_market`: **point in time**, not a historical reconstruction of what was held at the end of that specific day. Every `items` row currently `in_stock`, `reserved` or `listed_ebay` is summed as `cost * qty` for cost, and for market, `qty` times the latest `price_snapshots.gbp_market` for that item's card or retro title **and finish** when one exists, else `market_at_intake`. **Finish-aware**: a normal and a holo copy of the same card are two different things to price, so the snapshot lookup matches `finish` exactly (blank matches blank, never every finish at once) rather than reading whichever finish was fetched most recently regardless of which finish the item actually is (`pb_hooks/adapters/pricing_policy.js`'s own `snapshotsFor` uses the same rule). Because this reads current stock rather than a snapshot frozen on the day, a rebuild of a much older date shows today's stock levels, not that day's - accurate for the ordinary case (the nightly cron rebuilds the last 7 days, a few hours after each midnight) and worth knowing for a manual backfill of an old range. This is also the one expensive part of building a row (a full scan of held stock plus a price lookup per item), so rebuilding several days at once computes it **once** and reuses it for every day in that batch, never once per day.
- `credit_issued` / `credit_redeemed`: `credit_ledger` rows created that day, split by sign - `credit_issued` is the sum of every positive `amount` (trade-in credit, a refund paid back to credit, a positive adjustment), `credit_redeemed` the sum of every negative `amount` as a positive figure (credit spent on a sale, a negative adjustment, expiry). This reads correctly regardless of which `reason` a row carries - `credit_ledger.reason = "sale"` covers both a sale spending credit (negative) and a refund returning it (positive), so reason alone cannot separate them; sign can.
- `points_earned` / `points_redeemed`: `points_ledger` rows created that day, split by sign the same way (`delta > 0` is earned, `delta < 0` is redeemed as a positive figure).
- `cash_variance`: the sum of `cash_sessions.variance` for sessions closed that day.
- `new_customers`: `customers` rows created that day.
- `returning_customers`: of the customers with a sale (by `occurred_at`) or a completed trade-in that day, how many also have an *earlier* sale (by `occurred_at`) or completed trade-in (before that day's start) - a repeat, not a first visit.

`POST /api/vault/stats/rebuild?from=YYYY-MM-DD&to=YYYY-MM-DD` (**admin**) upserts one row per day in the range, matched by date so a second rebuild of the same range updates the same rows rather than duplicating them. Bounded to 400 days, same refusal as the reports routes below. One day's own failure (an unreadable record, a query error) never sinks the rest of the range: each day is tried on its own, and the response and audit row both reflect what actually happened. Response: `{ "from", "to", "days": 7, "failed": [] }` - `days` is how many rows were actually written, `failed` a `{ date, error }` entry per day that was not (empty in the ordinary case). Audited unconditionally, whether every day succeeded or not: `collection: "daily_stats"`, `meta: { from, to, days, failed }` (`failed` as a count in the audit row).

A cron named `stats` rebuilds the **last 7 UTC days** (never today, which is still in progress) at 00:30 UTC, not only yesterday - a day's own row can still be missing something the night it happens (a late eBay orders import landing after 00:30, a refund processed the next morning against a sale from days before), so every night re-walks the past week and self-heals a day's row once the data it was missing actually exists. `POST /api/vault/stats/rebuild` covers a longer backfill or a one-off correction; the nightly cron is the routine case. `POST /api/crons/stats` (PocketBase's own "run this job now" route, superuser only) runs it on demand.

### `GET /api/vault/reports/:key`

```
GET /api/vault/reports/:key?from=YYYY-MM-DD&to=YYYY-MM-DD&group=day|week|month&by=<dimension>&compare=previous|none
```

**staff**; `compliance` and the separate `audit.csv` export below are **admin**. An unknown key (including a JavaScript `Object.prototype` name like `constructor` or `toString`, which a plain `builders[key]` lookup would otherwise resolve to something that is not a report) refuses with 404 `"Unknown report. Pick one of sales, buyins, margin, stock, channels, customers, loyalty, cash, compliance."` - the key is resolved and admin-gated **before** `from`/`to` are even looked at, so a caller who cannot see a report learns nothing about whether their date range would have been valid either. `from` and `to` are required; missing or malformed dates, or a real-looking but non-existent calendar date such as `2026-02-30`, refuse with 400 `"Pick a date range. Both from and to are needed, as YYYY-MM-DD."`; `from` after `to` refuses with 400 `"The from date is after the to date. Swap them over."`; a range over 400 days refuses with 400 `"Pick a range of up to 400 days."`. `group` defaults to `day` and falls back to it for any other value; `week` labels are always that week's **Monday**; `month` labels are `YYYY-MM`. `by` is report-specific (listed per key below) and falls back to that report's first-listed dimension when omitted or unrecognised. `compare` is `none` (default) or `previous`: a same-length window immediately before the range (`to` of the compare window is the day before `from`, and it spans exactly as many days as `from`..`to` does) - **never the previous calendar month or week**, even under `group=month`/`group=week`; a 45-day range's compare window is the 45 days before it, not "last calendar month".

Every response is the same envelope:

```json
{
  "key": "sales",
  "from": "2026-09-14",
  "to": "2026-09-20",
  "group": "day",
  "series": [ { "label": "2026-09-14", "values": { "...": 0 } } ],
  "table": [ { "...": 0 } ],
  "totals": { "...": 0 },
  "compare": { "totals": { "...": 0 }, "from": "2026-09-07", "to": "2026-09-13" } | null
}
```

`series` and `totals` for `sales`, `buyins`, `customers` and `loyalty` read `daily_stats` per day in range (falling back to a fresh, unsaved computation for any day the nightly cron has not reached yet, so a report is never wrong just because the build is behind, and batched into a single query for the stored days plus **one shared stock valuation for every unbuilt day in the batch**, not one full stock scan per missing day - see `daily_stats.stock_value_*` above); `table` (the `by=<dimension>` breakdown) and every report-specific figure not on `daily_stats` come from direct queries, bounded to the same range. `stock`, `channels`, `margin`'s markdowns, `cash` and `compliance` query directly throughout, since none of their shapes map onto a single day row. `stock`, `channels` and `compliance` return `series: []` - none of their figures are a day-by-day series (`stock` and `channels`' own point-in-time figures have no "day" to plot, and `compliance`'s register is a table, not a trend).

`compare=previous`'s `totals` carries **only the totals keys that builder has declared as period-scoped** (a real function of `from`/`to`), never the whole `totals` object unfiltered - several reports mix a genuine period figure (this period's revenue) with an "as things stand right now" one (stock valuation, everything currently on the want list, an item's current tier) that a second `build()` call over the *previous* period would only repeat identically; showing that repeated figure as if it were "the previous period's value" would be misleading, and for `stock`'s full-table scan, pointlessly expensive to even compute a second time. A report whose declared list would leave nothing to show (`stock` - only `sell_through` is period-scoped) skips the second `build()` call entirely and returns `compare.totals: {}`. Per key: `sales` - all of `revenue`, `count`, `avg_basket`, `heatmap`; `buyins` - `spend`, `count`, `avg_offer_pct`, `cash`, `credit`, `top_sellers` (not `items_bought`/`items_sold`/`sell_through_ratio` - a running conversion rate checked against items' *current* status, not a period sum); `margin` - `revenue`, `cost`, `margin`, `margin_pct`, `vat_estimate` (not `markdown_count`/`markdown_value` - a point-in-time proxy); `stock` - `sell_through` only; `channels` - `revenue`, `count`, `by_channel`, `items_ended` (not `listing_ages`); `customers` - `new`, `returning`, `top_by_spend`, `top_by_trade_in`, `credit_liability` (not `want_list_demand`); `loyalty` - `points_earned`, `points_redeemed`, `perk_usage`, `reward_take_up`, `referrals`, `programme_cost_pct` (not `tier_distribution`); `cash` - every totals key; `compliance` - every totals key.

Every report also serves `GET /api/vault/reports/:key.csv?...` (the same parameters) as a CSV of its `table`, `Content-Disposition: attachment`, `Cache-Control: no-store`, a header row from the table's column labels, and the same formula-injection guard `pb_hooks/lib/vaultutil.js`'s `csvCell` uses for the stock book (a cell starting with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with a quote and quoted). Every CSV export - a report's own `.csv` and the separate `audit.csv` below - is audited: `collection: <report key>` (or `"audit_log"` for `audit.csv`), `record: ""`, `meta: { from, to, rows }`; a plain JSON report read is not (this section's own opening paragraph explains why).

Keys:

- **`sales`** - revenue by period, **net of refunds** (gross `sales_total_by_payment` minus `sales_refunded`, see `daily_stats` above); `by`: `game` (default) | `kind` | `staff` | `payment`. `table` rows: `{ key, label, revenue, count }` (already net of discount and refund, per line, through the shared `saleline` evaluator). `series` values: `{ revenue, count, avg_basket }`. `totals`: `{ revenue, count, avg_basket, heatmap }` - `avg_basket` is `revenue / count` rounded half-up to the nearest penny (the shared `money.roundHalfUp`, never a float). `heatmap` is 7 arrays of 24 integers, sale counts by hour, **index 0 is Monday, 6 is Sunday**, hours 0 to 23 **in Europe/London civil time** (GMT or, roughly April to October, British Summer Time) - a staffing chart keyed to opening hours reads as the shop actually experiences them, unlike every day bucket elsewhere in this package (`group=day|week|month`, `daily_stats` itself), which stays plain UTC throughout; `pb_hooks/lib/reports/dates.js`'s `toLondon` is the one place that conversion happens, since goja has no reliable timezone database to lean on instead. `by=payment`'s bucket for a blank `payment` (an eBay-import sale) is labelled `(none)`, matching `sales_total_by_payment`'s `none` above.
- **`buyins`** - spend by period; `by`: `game` (default) | `staff`. `table` rows: `{ key, label, spend, count, avg_offer_pct }` (`avg_offer_pct` is populated for `by=game`, since offer percent is a line-level, per-card figure; it reads 0 on `by=staff` rows - the headline figure below covers all trade-ins regardless of dimension). `series` values: `{ spend, count }`. `totals`: `{ spend, count, avg_offer_pct, cash, credit, items_bought, items_sold, sell_through_ratio, top_sellers }` - `avg_offer_pct` is `offer_price / market_price * 100` averaged over every accepted line with `market_price > 0`, rounded half-up to 1dp; `items_bought` / `items_sold` **both count stock rows, not units** (the same row-level convention `stock`'s own `sell_through` uses - a trade-in line that became several stock rows, or one row holding several units, counts as that many, or that one, row bought), so the two figures - and `sell_through_ratio`, rounded half-up to 3dp - are always on the same scale; they are a running conversion rate for stock this shop has taken in, not bounded to items bought *and* sold within the same range. `top_sellers` is up to 10 `{ customer, name, count, spend }`, most trade-ins first. The CSV's `count` column is headed `Count`, not `Lines` - `by=game`'s `count` is accepted trade-in lines, `by=staff`'s is trade-ins themselves, and one header has to cover both.
- **`margin`** - gross margin; `by`: `game` (default) | `kind` | `staff`. Sale price is net of the sale-level discount and of every refund on file, through the same shared `saleline` evaluator the stock book and the refund route use (`pb_hooks/lib/shared/saleline.js`), so this can never disagree with either about what a line actually made. `table` rows: `{ key, label, revenue, cost, margin, margin_pct }` (`margin_pct` rounded half-up to 1dp). `series` values: `{ revenue, cost, margin }`. `totals`: `{ revenue, cost, margin, margin_pct, vat_estimate, markdown_count, markdown_value }`. `vat_estimate` is the margin-scheme VAT estimate: one sixth of the *positive* margin on lines whose item carries `tax_scheme: "margin"` (the VAT fraction of the standard 20 percent rate), zero whenever `settings.vat_registered` is off - an estimate for the reports screen, not a return. `markdown_count` / `markdown_value` are a proxy: every `items` row (any status) whose current `price` sits below its `market_at_intake`, valued at the difference - a proxy for "this was marked down", not a log of every price change actually made.
- **`stock`** - value at cost vs market, ageing, sell-through, dead stock and price movers, `series: []` (nothing here is a day-by-day figure). Everything except sell-through is **point in time** (as stock stands when the report runs), the same caveat as `daily_stats.stock_value_*` above, and **finish-aware** the same way: a card's price movers and its ageing/dead-stock valuation both price each item off its own finish's latest `price_snapshots` row, never a different finish of the same card. `by`: `game` (default) | `set`, for sell-through only. The primary `table` (and its CSV) is **price movers**: `{ item_id, sku, title, market_at_intake, latest_market, pct_change }` (`pct_change` rounded half-up to 1dp) for every held item (`in_stock`, `reserved` or `listed_ebay`) whose card or retro title has a `price_snapshots` row *at that item's own finish* and whose latest `gbp_market` differs from `market_at_intake` by more than 15 percent either way, sorted by the size of the move, `item_id` included so the app can offer a one-click reprice. `totals`: `{ value_cost, value_market, unrealised_gain, ageing_buckets, sell_through, dead_stock, price_movers_count }`. `ageing_buckets` is always **5** rows, `{ bucket, min, max, count, value_cost, value_market }` for `"0-30"`, `"31-90"`, `"91-180"`, `"180+"` and **`"unknown"`** days since `acquired_at` (`max` is `null`, never a value that cannot round-trip through JSON, on the open-ended `"180+"` bucket, and both `min`/`max` are `null` on `"unknown"`) - an item with no `acquired_at` on file is not evidence it was freshly acquired, so it gets its own bucket rather than being miscounted into `"0-30"`; the same item is left out of `dead_stock` below, for the same reason (its age genuinely is not known, not "definitely not over 180 days"). `sell_through` is `{ key, label, acquired, sold, rate }` per game or set (`rate` rounded half-up to 3dp): **stock rows**, not units - a sealed line of qty *n* is one row, and since a sale decrements `items.qty` in place, a partly-sold multi-quantity row's original quantity cannot be recovered from its current state, so a row only counts as sold once it has sold out completely (`status = "sold"`). `dead_stock` is `{ item_id, sku, title, days_held, cost, market }` for every held item over 180 days since a *known* `acquired_at` - the `"180+"` ageing bucket's own rows, `"unknown"` excluded.
- **`channels`** - in-store vs eBay, `series: []` (nothing here is a day-by-day figure). `table` rows: `{ key, label, revenue, count }`, keyed on **`sales.channel`** (`"counter"` when blank, `"ebay"` when set - a *sale's* channel, never an item's own eBay fields), revenue net of refunds. `totals`: `{ revenue, count, by_channel, listing_ages, items_ended }`. `listing_ages` is `{ item_id, sku, title, days_listed }` for every item currently `status = "listed_ebay"` - `days_listed` reads `items.listed_at` (set by an `onRecordUpdate` hook in `pb_hooks/items.pb.js` the moment `status` most recently became `listed_ebay`, cleared when it leaves that status again) falling back to `acquired_at` for the rare row neither the hook nor this phase's backfill migration has reached; `days_listed` is `null`, never a false "0 days", when neither field is set. `items_ended` counts items whose `status` is no longer `listed_ebay`, whose `updated` falls in range, and that were on eBay at all - `ebay_listing_id != "" || ebay_sku != ""`, not `ebay_listing_id` alone: nothing in this backend writes `ebay_listing_id` (docs/PLAN.md's eBay round trip is planned, not built), and a Card Uploader listing carries `ebay_sku` (docs/api-contract.md's "Phase 4: exports, imports and SumUp"). A proxy either way, since there is no dedicated "ended" status.
- **`customers`** - new vs returning; top by spend and by trade-in; credit liability; want-list demand. `table` rows mirror the top-by-spend list: `{ customer, label, amount }`. `series` values: `{ new, returning }`. `totals`: `{ new, returning, top_by_spend, top_by_trade_in, credit_liability, want_list_demand }`, the first two up to 10 `{ customer, name, amount }` each, **`top_by_spend`'s `amount` net of refunds** (each sale's own `total` minus its own `refunded_total`) - `top_by_trade_in` has no equivalent "refund" to net off a completed buy-in's payout. `credit_liability` is the sum of every `credit_ledger.amount` created on or before the end of the range - never `customer_private.credit_balance`'s cache - which is also each customer's own recomputed balance summed across every customer, for free. `want_list_demand` is `{ key, card_id, label, count, in_stock }` for open `want_list` rows grouped by card (or by free text when there is no card), most-wanted first, `in_stock` true when the shop currently holds a matching item.
- **`loyalty`** - points issued/redeemed, tiers, perks, rewards, referrals, programme cost. `table` rows are the tier distribution: `{ tier, label, count }` (plus a `{ tier: "", label: "No tier", count }` row when any `customer_private` row has none). `series` values: `{ points_earned, points_redeemed }`. `totals`: `{ points_earned, points_redeemed, tier_distribution, perk_usage, reward_take_up, referrals: { total, earned }, programme_cost_pct }`. `perk_usage` is `{ perk_type, used_count }` summed over `perk_usage` rows created in range; `reward_take_up` is `{ reward, label, count, points_spent }` per reward, from `reward_redemptions` created in range. `programme_cost_pct` (rounded half-up to 1dp) values the points redeemed in range at the programme's `points_per_pound_redemption` (the shared `pointsToPence`, `pb_hooks/lib/shared/loyalty.js`) over sales revenue **net of refunds** for the same range.
- **`cash`** - sessions, variance history, cash in/out. `table` rows are the sessions closed in range: `{ session_id, opened_at, closed_at, expected, counted, variance }`. `series` values: `{ variance }`, one entry per day/week/month in range (0 where nothing closed). `totals`: `{ variance_total, session_count, cash_in, cash_out, by_day }`, `by_day` a `{ date, in, out }` row per day from `cash_movements.amount`'s sign (matching `pb_hooks/lib/vaultutil.js`'s own reasoning: money out is stored negative).
- **`compliance`** (**admin**) - the buy-in register: `table` rows `{ id, number, completed_at, seller_name, seller_address, id_type, items, total_offer }` for every trade-in completed in range. `totals`: `{ count, stock_book_url }`, `stock_book_url` a ready-made link to `GET /api/vault/exports/stock-book` for the same range (that route itself is unchanged - see the Phase 2 section above).

`GET /api/vault/reports/audit.csv?from=YYYY-MM-DD&to=YYYY-MM-DD` (**admin**) streams `audit_log` for the range as CSV (`created, actor, action, collection, record, meta, ip`, `meta` as a JSON string cell), the same formula-injection guard, `Content-Disposition: attachment`. Audited: `collection: "audit_log"`, `meta: { from, to, rows }`.

### Saved and scheduled reports

`saved_reports` rows (`owner`, `report_key`, `filters` json, `name`, `schedule`: `none` | `weekly` | `monthly`, `recipients`) are ordinary collection-API records. **A staff member may list, view, create, update or delete only their own rows** (`owner = @request.auth.id`); an admin may do any of those to any row (this phase's own migration tightens the seeded rule from `1789819560_ops_collections.js`, which was staff-wide). **Setting `recipients` or `schedule` needs `role = "admin"` either way**, even on a staff member's own row - the two fields that decide whether and to whom a row is ever emailed, gated the same `@request.body.<field>:isset = false` way `notifications`' own rule already gates its staff-only fields. `filters` holds `{ by, group }` only - `from` and `to` are never read from a saved row for a scheduled send; the period is always computed fresh from the schedule (see below), so a saved weekly report always covers the week that just ended, never a stale literal date. `recipients` is an array of email addresses, re-validated by the sending cron itself (well-formed shape, de-duplicated, capped at 10) rather than trusted as saved - a row written before the rule above existed, or straight against the database, is not assumed to be safe unseen; when empty (or empties out after validation), the send falls back to the owner staff member's own email, and is skipped (logged, not failed) when neither exists.

**Admin-only report keys (`compliance` today) are only ever sent while the row's own owner is a current admin** (`role = "admin"` and `active = true`), re-checked by the cron itself at send time, every send, regardless of who could set `recipients`/`schedule` when the row was saved - an owner demoted after saving the row, or a row written straight against the database bypassing collection rules entirely (which a superuser-run cron itself also does), must not go on quietly leaking a compliance report to whoever is listed. A row that fails this check is **skipped**, not built or sent, and audited: `collection: "saved_reports"`, `record: <saved_reports id>`, `meta: { reason: "admin_only" }`, action `saved_report_skipped`. This is defence in depth on top of the collection rule above, not a substitute for it: the two are meant to agree, and only the cron's own check can ever be the one that actually stops an email going out.

Two crons, matching "a cron at 08:00 UTC on Mondays sends every weekly saved report and on the 1st sends the monthly ones": `scheduled_reports_weekly` (`0 8 * * 1`) sends every `schedule: "weekly"` row for the Monday-to-Sunday week that just ended; `scheduled_reports_monthly` (`0 8 1 * *`) sends every `schedule: "monthly"` row for the calendar month that just ended. Which day either one runs on is the **cron expression alone** - neither handler re-checks the date itself, so `POST /api/crons/scheduled_reports_weekly` or `POST /api/crons/scheduled_reports_monthly` (PocketBase's own "run this job now" route, superuser only) sends unconditionally whatever day it is actually run, exactly as the schedule would have.

Each send emails the report's `totals` as plain text (one line per numeric figure, money through the shared `formatGBP` for exactly the keys that report's own builder declares as money - an explicit, per-report list, never a guess from the field's name) with its `table` attached as a CSV, through the app mail client the way `pb_hooks/lib/receipts.js` does, honouring `settings.email.test_mode` (logs `"[scheduled_reports:test_mode] would email ... (not sent)"` instead of sending). Every send, sent or logged, is audited by the saved report's id alone, action `saved_report_sent`: `collection: "saved_reports"`, `record: <saved_reports id>`, `meta: { sent, test_mode }`.

`POST /api/crons/{name}` returns 204 once the job is *queued*, not once it has finished - a job that does real work (building a report, sending mail) can still be running after the response comes back; a caller checking its audit row should poll briefly rather than checking once, immediately.

### The Monday digest

At 08:00 UTC every Monday (`weekly_digest` cron, alongside the scheduled-reports cron above), every admin (`staff` with `role = "admin"`, `active = true` and a non-empty `email`) is emailed the week that just ended: sales, buy-ins, margin, new customers, cash variance, and the three biggest price movers over 15 percent, in plain text with every £ figure through the shared `formatGBP`. `settings.email.test_mode` logs the would-be body instead of sending. Audited whether sent or logged: `collection: "settings"`, `meta: { sent, test_mode, recipients, movers }` - `movers` is the three movers' SKUs, one of the field labels `pb_hooks/audit.pb.js` already treats as safe to record. `POST /api/crons/weekly_digest` runs it on demand and, since the digest never re-checks the day itself, works the same way any day it is called.

### Implementation notes (as built in Phase 4)

- **UTC day boundaries throughout**, compared in PocketBase's stored form (a space, not a "T") - `pb_hooks/lib/reports/dates.js` is the one place that builds them. The one deliberate exception is the sales heatmap's own hour and weekday, which read in Europe/London civil time (`dates.js`'s `toLondon`, hand-rolled since goja has no reliable timezone database) - see the `sales` key above.
- **Net of refunds, everywhere a revenue figure is shown.** `daily_stats.sales_refunded` (the day's sales' own `refunded_total`, summed) is the one field every report's revenue subtracts from the gross sales total to arrive at what was actually kept; `daily_stats.sales_total_by_payment` itself stays gross (what was actually taken by each method) and is never adjusted. A line-level figure (`margin`'s revenue, the `sales` `by=<dimension>` table) was already net of refunds from Phase 2 onward, through the shared `saleline` evaluator's `cumNet` - only the day-level and report-total figures needed `sales_refunded` added to reach the same standard.
- **`sales_total_by_payment` has six keys, not five**: the five `sales.payment` values plus `none`, for a sale an eBay order import created with no shop-side payment (docs/api-contract.md's "Phase 4: exports, imports and SumUp" section, `sales.channel` / `sales.external_ref`). `sales_count` and every report's revenue total already include these sales; only the payment-method bucketing needed the extra key so they are not misread as `"mixed"`.
- **The channels report keys off `sales.channel`, never an item's own eBay fields** - `items.ebay_listing_id` / `.ebay_sku` are about a listing's own lifecycle (its age, whether it has ended), which stays a separate figure on the same report rather than standing in for which channel a sale went through. Where an item's own "was this on eBay" matters (`items_ended`), it reads `ebay_listing_id != "" || ebay_sku != ""` - nothing in this backend writes `ebay_listing_id` yet, only `ebay_sku` (the Card Uploader import), so `ebay_listing_id` alone would miss every real listing on file.
- **Every sales figure reads `sales.occurred_at`, never `sales.created`** - `sale_lines` reaches it through the relation (`sale.occurred_at`), since the field lives on `sales` only. A refund has no `occurred_at` of its own and keeps the date logic it already had (the net-of-refunds figures still read live `refunded_qty` / `refunded_total`, whatever day that refund happened on).
- **Stock value and every `stock` report figure except sell-through are point in time**, not a reconstruction of a past day - said so above and repeated here because it is the one place a "build for date X" request can silently mean something other than what it asks for. The same figures are also **finish-aware**: the price lookup behind them matches a stock item's own `finish` exactly (blank matches blank, never every finish at once), so a normal and a holo copy of the same card are priced independently rather than one silently borrowing the other's latest snapshot.
- **`compare=previous` only ever recomputes and returns totals a report has itself declared period-scoped** (`PERIOD_SCOPED_TOTALS` per builder, `pb_hooks/lib/reports/*.js`) - a point-in-time figure (stock valuation, the want list, tier distribution) does not get a second, misleadingly-labelled "previous period" value, and a report with nothing period-scoped to show (`stock`) skips the second `build()` call - and its cost - entirely.
- **Sell-through, and `buyins`' items bought/sold, count stock rows, not units** - a sealed line's original quantity is not recoverable once it has partly sold (PLAN.md: "a sale decrements qty"), so a multi-quantity row only counts as sold once it is fully gone, and the "bought" side of the same ratio counts rows the same way so the two sides are on the same scale.
- **A blank `acquired_at` is "unknown", never miscounted as "0 days old"** - the stock report's ageing buckets carry a fifth, open `"unknown"` bucket for it (`min`/`max` both `null`), and `dead_stock` leaves such an item out rather than guessing it is either fresh or dead.
- **The margin-scheme VAT estimate is one sixth of the positive margin on margin-scheme lines**, zero when `settings.vat_registered` is off - an estimate for the screen, never a return, and never invented when the shop's VAT status is not on record (CLAUDE.md's "Pricing").
- **Markdowns are a proxy** (current `price` below `market_at_intake`), not a log of every reprice - said so on the report itself as well as here.
- **`credit_issued` / `credit_redeemed` and `points_earned` / `points_redeemed` split by the ledger row's sign**, not by its `reason` - `credit_ledger.reason = "sale"` alone covers both a sale spending credit and a refund returning it, so sign is the only reliable split.
- **Every percentage is rounded half-up to 1 decimal place, every ratio to 3**, through one shared helper each (`query.roundPct` / `query.roundRatio`, `pb_hooks/lib/reports/query.js`) rather than a `Math.round` written out fresh at each call site.
- **The 400-day bound and its message are shared** by `GET /api/vault/reports/:key` (and its `.csv` and `audit.csv` variants) and `POST /api/vault/stats/rebuild`: `"Pick a range of up to 400 days."` A calendar date that is only shaped like `YYYY-MM-DD` but does not exist (`2026-02-30`) is refused the same way as a missing or malformed one, not passed through to a downstream `new Date(...)` that would silently misparse it.
- **A report key is resolved with `hasOwnProperty` and a `typeof` check on what it names, not a bare `builders[key]` truthiness test** - a path segment that happens to name something on `Object.prototype` (`constructor`, `toString`, `hasOwnProperty` itself) is a real, if unlikely, request a router does not get to choose not to receive, and must 404 the same as any other unrecognised key rather than resolving to that inherited value.
- **Admin gating happens before date validation, not after** - a caller who cannot see a report (`compliance`, `audit.csv`) is refused before `from`/`to` are even looked at, so they learn nothing about whether their date range would otherwise have been accepted.
- **Every CSV export - a report's own `.csv` and `audit.csv` - is audited**, not only `audit.csv` as originally shipped; a plain JSON report read still is not, for the reason given where that is first said.
- **`daily_stats` is matched by date as a same-day range**, never text equality, for the same reason every other date field in this codebase is - PocketBase's stored form is a full timestamp, and a bare date string is not it. `upsertDayRow` / `upsertDayRows` (`pb_hooks/lib/reports/daily.js`) find-or-create this way, so rebuilding the same range twice never produces a second row for a day.
- **A multi-day rebuild, or a report falling back to several unbuilt days at once, scans the stock table once, not once per day** - `daily.js`'s `currentStockValuation` is computed a single time and threaded through every `buildDayRow` call it covers (`upsertDayRows`, `rowsForEachDay`), rather than repeating a full items scan plus a price lookup per item for an answer ("stock value right now") that would come out identical every time in the same batch.
- **A per-parent-id loop over a child collection (a trade-in's lines, a sale's lines, the items sold from a trade-in) is one batched query, not one query per id** (`query.queryByIds`, chunked at 200 ids per query so a very large id list is still a handful of queries, never one filter of unbounded length) - `buyins`, `margin`, `sales`' `by=<dimension>` table and `compliance` all read this way now.
- **An unbounded list load with no date range to bound it (the want list, `compliance`'s trade-in register) is read in fixed-size pages** (`query.findAllByFilter`, 500 rows per page), not one call asking PocketBase to hold every matching row in memory at once.
- **No `Infinity`, `NaN` or other non-JSON value ever reaches a response body.** The stock report's open-ended ageing bucket uses `max: null`, not `Infinity` - a JS value that is not valid JSON will fail partway through response encoding after the 200 status and some bytes are already on the wire, producing a truncated body a client reads as a connection or parsing failure rather than a clean error. Worth restating because it is easy to reach for `Infinity` for "no upper bound" and it reads fine in every local test until a client actually parses the response.
- **Dependencies**: none added. Every helper reused (`pb_hooks/lib/vaultutil.js`, `lib/audit.js`, `lib/csv.js`, `lib/shared/{money,loyalty,saleline}.js`) already existed.

## Implementation notes (as built in Phase 2)

Where the routes differ from the text above, the built behaviour is the truth and this list records it.

- `POST /api/vault/step-up` returns 400 for a wrong password (403 is only for a missing or expired token on a protected route). The signing key is derived from the app settings and peppered with `GG_ID_PHOTO_KEY`.
- `trade_ins.number` is optional with a partial unique index, so drafts can be created through the collection API; the number is assigned at completion.
- `trade_in_lines` carry `kind`, `game` and `completeness` (items need a kind and a game, and sealed or accessory lines have no card to derive them from). The completion route still falls back to the linked card or retro title when they are empty.
- `trade_in_lines` also carry `override_reason`, `override_cash`, `override_credit` and `cosmetic_grade`. **A line is overridden when `override_reason` is non-empty**; `override_cash` and `override_credit` are what the staff member typed for each payout type, and `offer_price` stays the figure actually paid for the type chosen, so the payout arithmetic is unchanged. Completion copies `cosmetic_grade` (A, B or C) onto `items.cosmetic_grade` for retro lines only, and lists the overridden line ids in the audit meta as `overridden_lines`. The reason stays on the line row and never reaches `audit_log`.
- **A bulk lot is one ordinary line**, not a special shape: `kind: "other"`, `qty: 1`, the flat figure in both `offer_price` and `market_price`, `market_source: "Bulk lot"` and a title such as "Bulk lot, 400 cards". It becomes a single `items` row of kind `other` and `qty` 1 with one label job, and the receipt and the stock book read it like any other line.
- Receipt JSON takes its terms from `settings.receipt_terms`; the signature is served through a short-lived PocketBase file token, never as a data URL. Email goes through PocketBase's own SMTP settings (`$app.newMailClient()`), so the admin UI's mail settings must be filled in; `settings.email` holds only the from name, from address, reply-to and `test_mode`.
- Response supersets: `cash-sessions/close` adds `expected`, `variance` and `variance_alert`; `sales/:id/refund` adds `refunded_total`, `points_reversed`, `credit_balance` and `points_balance`.
- **A refund never rewrites what was sold.** `sale_lines.qty` and `.discount` are the as-sold figures for good; a refund moves `sale_lines.refunded_qty` and `sales.refunded_total`, and sets `sale_lines.status = "refunded"` once `refunded_qty` reaches `qty`. Amounts are worked out from the immutable figures: `lineGross = unit_price * qty - discount`, the sale-level discount is allocated across the lines pro rata with the last line (by created, then id) absorbing the rounding remainder, `lineNet = lineGross - allocation`, and refunding `r` more units of a line pays `roundHalfUp(lineNet * (refunded_qty + r) / qty) - roundHalfUp(lineNet * refunded_qty / qty)`. Any sequence of partial refunds therefore sums to exactly `sales.total`. Points reverse the same way, cumulatively over `refunded_total`, and the points ledger is allowed to go negative.
- **The refund reason is a `notes` row** against the sale (`target_collection = "sales"`), not audit meta; the audit row carries only the note's id. `audit_log` is permanent and superuser-only, and a refund reason is free text about a named customer.
- **`trade_ins.signature` and `quotes.photos` are protected files.** They are only served with a short-lived PocketBase file token, and that token is minted from the **calling staff auth record** (`e.auth.newFileToken()`): `record.newFileToken()` throws "not an auth collection record" on an ordinary record. The receipt route mints one and appends it to `signature.url`. `items.photos` stays public: that is product imagery.
- **The cash ID gate needs a photo, not just fields.** A cash payout requires an `id_documents` row for that customer whose photo file is still present, or an `id_check.id_document` in the same call belonging to them; otherwise 422 "Take a photo of the customer's ID before paying cash." The document's id goes on `trade_ins.id_document`, and its `expires_at` is pushed out to now plus `settings.id_photo_retention_months` on every cash completion, so a photo lives twelve months from the last cash buy-in rather than from the day it was taken. `customer_private.flags` is honoured first: `no_cash` is 422 "This customer is marked no cash. Pay as store credit." and `under_18` is 422 "This customer is recorded as under 18, so we cannot buy for cash."
- **`settings.cash_cap` of 0 means no cash at all**, not "no limit": 422 "Cash payouts are switched off in settings." on a buy-in and "Cash sales are switched off in settings." on a sale.
- Completion also validates before it writes: `id_check.id_ref_last4` must be 1 to 4 characters, and a supplied signature must be a PNG under 2 MB.
- **Points earned spread the sale-level discount across the lines** before the evaluator sees them, so the gross it earns on is the amount actually charged. A sale with no customer has `points_earned` 0.
- **One open cash session is enforced by a partial unique index**, not just by a read: `cash_sessions (closed_at) WHERE closed_at = ''`. Opening runs in a transaction and a collision on that index comes back as the same 409.
- Every CSV cell that opens with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with a single quote and quoted, so a seller called `=HYPERLINK("x")` reads as text in a spreadsheet. Money columns stay numeric, negative margins included.
- The stock book is **one row per sale line** for the quantity still sold (cost is the unit cost times that quantity, sale price is the line's net less what has been refunded off it, margin is the difference), plus one row for the quantity still on the shelf with the sale columns blank. A fully refunded line produces no row. The purchase columns repeat on every row of an item.
- `GET /api/vault/config` and `GET /api/vault/customers/:id/id-document` write no audit row: both are loaded by ordinary counter screens and neither returns anything sensitive.
- The retention cron purges expired `id_documents` (file included, audited by id) and notifications older than 12 months; quote photos are not purged yet because `quotes` has no closed-at timestamp (lands with the portal phase). Its cutoffs are formatted the way PocketBase stores a date (a space, not a `T`), so they compare correctly as text.
- `GG_ID_PHOTO_KEY` (exactly 32 characters) is required in production; without it the ID check route refuses with 500 and photos cannot be stored.
- ID photo bytes go into `$security.encrypt` as an array of numbers and come back through `toBytes($security.decrypt(...))`, so nothing on that path is base64'd. `pb_hooks/lib/base64.js` is now only the signature data URL's codec.
- The refund route and the stock book both price through the shared `saleline` evaluator (`packages/shared/src/saleline.ts`, built into `pb_hooks/lib/shared/saleline.js`), so the server and the counter's refund sheet cannot drift. The lines are always read in `created,id` order before the breakdown, via `vaultutil.saleLineRows`: lines written in one transaction share a `created` timestamp to the millisecond, and the rounding remainder has to land on the same line every time.
- The seeded `pricing_rules` single bands are condition wildcards. Condition is applied by `adjustForCondition` before a rule is picked, so a condition on the band would leave every non-NM single matching no rule at all.

## Phase 3: lookup, prices and FX

The catalogue and price adapters (`pb_hooks/adapters/*.js`), driving `cards`, `card_sets`, `retro_titles`, `price_snapshots` and `fx_rates`. Every route below needs a `staff` token; none needs admin or step-up. Money and error conventions are as above.

Two things worth stating plainly, since both read like they might be a mistake if you only see them once, in passing:

- **One Piece prices are stored under `source: "tcgplayer"`, not a separate `"optcg"` value.** The OPTCG API's `market_price` is TCGplayer-derived data (docs/PLAN.md: "OPTCG `market_price` as fallback" beside Cardmarket file 18), so it belongs in the same `price_snapshots.source` slot as every other game's TCGplayer figure, and the counter's source badge ("from TCGplayer") reads correctly for a One Piece card with no special case. `services/pricesync`'s own TCGCSV One Piece feed writes to the same slot; `chooseMarketPrice` takes the freshest row per source, so the two coexist without conflict.
- **`GET /api/vault/fx`'s `rates` are GBP per one unit of the foreign currency**, in both directions (EUR and USD): `rates.EUR = 0.8606` means one euro is worth 86.06 pence. Every conversion in this package and in `packages/shared/src/money.ts` reads a rate the same way, so a candidate's native amount is always multiplied by the rate it stands beside, never divided.
- **The lookup and search routes write no audit row; `refresh-prices` and `uk-comp` always do.** A catalogue search or an exact lookup is a read against public reference data (`cards`/`card_sets` list and view rules are public), the same reasoning `GET /api/vault/config` and the id-document lookup already use. `refresh-prices` audits the card or retro title id, the finish/completeness asked for, and the list of sources that actually returned a usable figure (`meta: { finish, sources: ["cardmarket", "ebay_uk_asking"] }`); `uk-comp` audits the id, finish/condition or completeness, and the price - never a customer.

`GET /api/vault/lookup?game=<key>&q=<text>`

`game` is one of `pokemon`, `mtg`, `yugioh`, `onepiece`, `lorcana`. Searches that game's adapter (name, or the "set number" forms `sv151 199` / `blb 223` for Pokemon/MTG/Lorcana, `OP01-001` / `CT13-EN003` for One Piece/Yu-Gi-Oh!), writes every match through to `cards` (and `card_sets` when the set is new), and returns at most 25 rows:

```json
{ "cards": [ { "id": "...", "game": "...", "set": "...", "set_code": "sv03.5", "set_name": "151", "number": "199", "name": "Charizard ex", "rarity": "Special illustration rare", "image_small": "...", "image_large": "...", "finishes_available": ["holo"], "external_ids": { "tcgdex": "sv03.5-199" }, "last_synced": "..." } ] }
```

A "set number" query is treated as an exact lookup and gets the same cache as the dedicated exact route below: a `cards` row whose `last_synced` is under 30 days old is returned straight from the database, with no adapter call at all. A plain name search always asks the adapter (discovering a card that is not in the database yet is the point of it), so it is never itself served from cache.

The two-token "set number" form is only recognised as an exact lookup when the second token actually looks like a collector number (digits, an optional trailing letter, or Lorcana's `n/total`) **and** the first token resolves to a real set - otherwise it falls through to a name search. This is what keeps a plain two-word name (`"charizard ex"`, `"lightning bolt"`) from being misread as an exact lookup for a set called "charizard" or "lightning". `sv151` is a shorthand alias for TCGdex's own set id `sv03.5` (players call Scarlet & Violet 151 "sv151"; the adapter itself does not), resolved through a small per-game alias table before anything else is tried; every other set token is resolved case-insensitively against `card_sets`, running that game's set sync once inline first on an install that has no `card_sets` rows for it yet (the same write the weekly cron does, pulled forward the moment it is actually needed, stamped so a game whose sync keeps failing is not retried on every request).

`GET /api/vault/lookup/:game/:set/:number`

The exact card, same row shape as above, wrapped in `{ "cards": [ ... ] }` (one row, for the same shape every lookup response uses). 30-day cache as above. 404 `"Card not found in <set name>. Check the number or add it manually."` (the set's own name once known, its code otherwise) when the adapter has nothing either.

`GET /api/vault/cards/:id/prices?finish=<finish>&condition=<NM|LP|MP|HP|DMG>`

Reads `price_snapshots` only - **never calls an adapter**, so a routine price check makes no outbound call at all; only `refresh-prices` and `uk-comp` below write anything.

```json
{
  "chosen": { "source": "cardmarket", "gbp_market": 31674, "native_currency": "EUR", "native_market": 36830, "fx_rate": 0.86, "fx_date": "2026-09-20", "fetched_at": "...", "stale": false, "evidence_url": "" } ,
  "sources": [ /* same shape, one row per source that has a value, in settings.source_priority order, every stale one flagged rather than hidden */ ],
  "condition_adjusted": 26923
}
```

`chosen` is `null` and `condition_adjusted` is `null` when there is no snapshot at all for that card and finish. `native_market` and `native_low`/`native_mid`/`native_trend` (on each `sources` row) are minor units of `native_currency`, exactly as stored; `gbp_market` sits beside them on the same row, per CLAUDE.md's "Pricing" (a foreign amount is never returned on its own). Freshness (`stale`) is UK sold comp 30 days, eBay asking 24 hours, Cardmarket and TCGplayer 3 days, either PriceCharting region 3 days - a stricter eBay window than `packages/shared/src/pricing.ts`'s own `DEFAULT_FRESHNESS` (48 hours), passed as this route's own policy to the shared `chooseMarketPrice` rather than its default. `condition_adjusted` is `chosen.gbp_market` after `settings.condition_multipliers` for `condition` (default `NM`).

`condition` is case-insensitive (`nm`, `NM` and ` Nm ` all normalise the same way) and defaults to `NM` when left out; a value other than `NM`, `LP`, `MP`, `HP` or `DMG` is refused with 400 `"Pick a condition: NM, LP, MP, HP or DMG."` rather than silently pricing at the wrong condition. Every route below that takes a `condition` validates it the same way.

`POST /api/vault/cards/:id/refresh-prices` with `{ "finish": "...", "condition": "NM" }`

Bypasses the price cache: calls the card's game adapter's `getPrices` plus eBay (when `settings.api_keys.ebay` is set; `condition` is folded into the eBay search text and its own cache key, so a fresher condition never reads another condition's cached asking price), converts every candidate to GBP pence at the latest `fx_rates` row, writes one `price_snapshots` row per source that returned a usable figure, and returns the same body as the GET, freshly recomputed. A foreign candidate is silently skipped (not written, not chosen) when no `fx_rates` row exists yet to convert it - "never returned on its own" applies to a rate-less conversion too, not just to the response shape. Audited: `collection: "cards"`, the card id, and `meta: { finish, sources }` naming every source that actually wrote a row.

`POST /api/vault/cards/:id/uk-comp` with `{ "finish", "condition", "price": <pence>, "url": "https://www.ebay.co.uk/itm/...", "sold_at": "YYYY-MM-DD" }`

Writes a `price_snapshots` row (`source: "uk_sold_manual"`, native and GBP both `price`, `fx_rate: 1`, `evidence_url: url`, `fetched_at` set to `sold_at`), audits it (the card id, finish, condition and price - no customer data is ever involved), and returns the same `{ chosen, sources, condition_adjusted }` body as the GET, so the UI can confirm the new comp was actually chosen. 400 `"Enter the sold price in pence, over zero."` when `price` is zero or negative; 400 `"That price looks too high. Check it is in pence, not pounds, and try again."` above £50,000 (5000000p) - the shop's own sanity ceiling on a hand-typed figure, not a card value limit. 400 `"That is not an ebay.co.uk item link. Paste the listing's own URL (ebay.co.uk/itm/...)."` when the URL is not `https://(www.)ebay.co.uk/itm/...`; 400 `"That sale date is in the future."`; 400 `"That sale is more than 30 days old. A UK sold comp only counts as fresh within 30 days."` (30 whole calendar days, compared at UTC midnight, so a comp sold exactly 30 days ago is still accepted regardless of what time of day it is now).

`GET /api/vault/retro/lookup?q=<text>&platform=<key>`

IGDB search (`platform` is one of `platforms.key`, mapped to IGDB's own numeric platform id) writing through to `retro_titles` (name, platform, cover; `external_ids.igdb`) when a `platform` is given - `platform` is a required field on `retro_titles`, so a search with no platform is preview-only (`id: ""` on every row, nothing written). 422 `"Retro title search needs an IGDB key. Add settings.api_keys.igdb first."` when that key is not configured; 502 `"IGDB did not answer. Try again, or add the title manually."` when the key is configured but the call to IGDB itself fails, so that never silently reads as "no such title". A title is written through regardless of whether its cover art could be fetched - the cover is best-effort and its own failure is never a reason to lose the title.

```json
{ "titles": [ { "id": "...", "platform": "...", "name": "Super Mario Kart", "region": "", "cover": "...", "external_ids": { "igdb": "1074" } } ] }
```

`GET /api/vault/retro/:id/prices?completeness=<loose|boxed|cib>`

Same shape as the cards GET above (`chosen`, `sources`, and `condition_adjusted: null` - condition multipliers are a TCG-card concept, not a retro one). `retro_source_priority` order (UK sold comp, PriceCharting PAL, eBay UK asking, PriceCharting NTSC). `completeness` is read off `price_snapshots.finish` - PLAN.md's data model gives `price_snapshots` one such column, shared by a card's finish and a retro item's completeness, rather than adding a second that would mean the same thing.

`POST /api/vault/retro/:id/refresh-prices` with `{ "completeness": "loose" | "boxed" | "cib" }`

Bypasses the price cache: calls PriceCharting (PAL category first, NTSC only when PAL has no entry, matched by the response's own `console-name` text rather than a URL slug - a differently-punctuated slug can never silently mislabel one region as the other) plus eBay UK asking (when `settings.api_keys.ebay` is set), converts every candidate to GBP pence at the latest `fx_rates` row, writes one `price_snapshots` row per source that returned a usable figure against this `retro_title`, and returns the same body as the GET, freshly recomputed. 422 `"PriceCharting is not set up. Add the key in Settings or enter a UK comp."` when `settings.api_keys.pricecharting` is not configured - PriceCharting is the one source this route exists to call, so it refuses cleanly up front rather than silently doing nothing useful; a UK comp still works with no key at all. Audited: `collection: "retro_titles"`, the title id, and `meta: { completeness, sources }` naming every source that actually wrote a row.

`POST /api/vault/retro/:id/uk-comp` with `{ "completeness", "price": <pence>, "url": "https://www.ebay.co.uk/itm/...", "sold_at": "YYYY-MM-DD" }`

The same body and rules as the card version, with `completeness` standing in for `finish` and `condition` (retro has neither) - `price_snapshots.finish` is written from `completeness`, as above. Writes a `price_snapshots` row (`source: "uk_sold_manual"`, native and GBP both `price`, `fx_rate: 1`, `evidence_url: url`, `fetched_at` set to `sold_at`) against this `retro_title`, audits it (the title id, completeness and price only), and returns the same `{ chosen, sources, condition_adjusted: null }` body as the GET. Same 400s as the card version: a price of zero or below, a price over the £50,000 sanity ceiling, a non-`ebay.co.uk` item URL, a sale date in the future, or a sale more than 30 days old.

`GET /api/vault/fx`

```json
{ "base": "GBP", "rates": { "EUR": 0.8606, "USD": 0.75 }, "date": "2026-09-18", "fetched_at": "...", "stale": false }
```

Reads the latest `fx_rates` row only - the daily 07:00 cron (`crons.pb.js`) is the only thing that ever calls Frankfurter. `rates[code]` is **GBP per one unit of `code`** (so `£1 = €1 / 0.8606`), the same direction as every helper in `packages/shared/src/money.ts`. Stale after 3 days. With no `fx_rates` row at all (a fresh install before the first 07:00 run), returns `{ "base": "GBP", "rates": {}, "date": null, "fetched_at": null, "stale": true }` rather than an error. `date` is the ECB reference date the rate belongs to (a weekend fetch carries Friday's date), null for rows written before the column existed; the counter prints it in the conversion detail.

### Implementation notes (as built in Phase 3)

- **The GET price routes never call an adapter.** Only the two `POST .../refresh-prices` routes (cards and retro) do.
- **`price_snapshots.source` has no `"optcg"` value** (its enum is fixed by `packages/shared/src/pricing.ts`'s `PriceSource` union, which this package does not own) - see the plain statement above on why `"tcgplayer"` is the correct, not merely convenient, home for it.
- **eBay and PriceCharting cache their own OAuth tokens and, for eBay, the computed candidate itself** in the new `adapter_state` collection (superuser-only; see the Phase 3 migration), keyed by `card+finish+condition` (or `retro_title+completeness`) for eBay's 24-hour "asking price" cache (docs/PLAN.md). This is separate from, and in addition to, `price_snapshots`' own freshness windows above.
- **The eBay asking haircut lives at `settings.offer.ebayHaircutPct`** (an integer percent, alongside the other `offer` figures the settings editor already writes), read by `pb_hooks/adapters/ebay.js`'s own `haircutPctFromSettings(app)` and falling back to 15 when the key is absent. This is its one home: nothing else in this package reads a haircut figure from anywhere else.
- **Every adapter re-hosts an image it must not hotlink before writing anything.** YGOPRODeck and OPTCG images are fetched into `cards.image_file` (a new file field, capped at 2 MB and restricted to `image/jpeg`, `image/png`, `image/webp` and `image/avif` - see the Phase 3 migrations) the moment an exact lookup resolves them, never as a bare URL, even transiently; a name search against either game therefore returns `image_small`/`image_large` empty for a card the database has not resolved exactly yet, rather than a hotlinked URL a picker would render. Every fetched image is validated and its real type sniffed from its own first bytes before it is stored - never trusted from a `Content-Type` header or a URL's extension alone (`pb_hooks/adapters/images.js`).
- **A card image is never fetched from inside the item-create transaction.** TCGdex, Scryfall and Lorcast images may be linked directly; the first time an item is created against a card whose image is still a bare URL, `items.pb.js`'s `onRecordCreate` only *queues* that card (`adapters/images.enqueueImageCache`, a single fast write into `adapter_state`'s `image_queue` entry) rather than fetching anything itself - a buy-in creates every item inside one `$app.runInTransaction`, so a network call at that point would hold the whole transaction open for as long as the image host takes to answer. `crons.pb.js`'s new `image_queue` job (every 5 minutes) drains the queue off that path entirely; a URL that fails to cache (unreachable, over the size cap, not a recognised image format) is simply left as a bare URL and tried again the next time an item is created against that same card.
- **`GET /api/vault/retro/lookup`'s IGDB platform ids are hand-derived**, not confirmed against a live key (nobody on this build has one - see `pb_hooks/adapters/fixtures/igdb_HANDWRITTEN_*.json`). Confirm `pb_hooks/adapters/igdb.js`'s `PLATFORM_IGDB_IDS` against IGDB's own `/platforms` once a key exists. The same caveat applies to `pb_hooks/adapters/pricecharting.js`'s PAL/NTSC console-category slugs.
- **`fx_rates.date` is the ECB rate's own date** (Frankfurter's `date` field, distinct from `fetched_at`), stamped by the fx cron and preferred over `fetched_at` everywhere a rate's "as of" date is shown - at a weekend or a bank holiday Frankfurter keeps answering with the last trading day's rate under a fresh `fetched_at`, so reading fetch time there would claim a rate is more current than it is. The cron writes no row at all when every quote it asked for comes back non-positive (Frankfurter's own empty-day shape) - the previous row, itself at most a day or two old, is left standing rather than replaced with a row that has nothing usable in it.
- **`pb/scripts/check.sh` runs its whole throwaway server under `GG_ADAPTER_TRANSPORT_MODE=fixture`**, not the blanket `offline_fail` refusal Phase 3's first cut used: `pb_hooks/adapters/fixture_transport.js` answers a fixed set of known adapter calls from the same `pb_hooks/adapters/fixtures/` files `pb/scripts/check-adapters.mjs` unit-tests each adapter against, and still throws for anything it has no mapping for, so a route this build never intended to call out from still fails the check loudly rather than silently reaching the real network. This is what lets `check.sh` exercise a search, an exact lookup, `refresh-prices` and the image queue end to end, fixtures and all, rather than only the paths a fresh row's 30-day cache can serve with no call at all.

## Phase 4: exports, imports and SumUp

Every route below needs a `staff` token; **admin** also needs `role = "admin"`. Money and error conventions are as above. Every route writes one `audit_log` row (identifiers and counts only), the same as every other route in this contract, except the two eBay-listing/end-listing GETs and the plain exports, which follow the stock book's own precedent of auditing a bulk read (the filters used and the row count, never a customer or seller's details).

### Exports

All six responses below carry `Content-Disposition: attachment` and `Cache-Control: no-store`, and every CSV cell goes through the same formula-injection guard as the stock book (`lib/vaultutil.js`'s `csvCell`, reached here through the new `lib/csv.js`) - a seller, customer or title starting `=`, `+`, `-`, `@`, a tab or a carriage return reads as text, not a formula. Every money column is pounds and pence from an integer of pence, never a float in between (`lib/csv.js`'s `pounds()`, over `lib/vaultutil.js`'s `poundsCell`).

`GET /api/vault/exports/sumup.csv?since=YYYY-MM-DD&dry_run=1`

SumUp's own CSV import layout (docs/csv-formats.md, "SumUp item import"): `Item name, Description, Category, Price, SKU, Barcode, Quantity, Tax rate (%), Variations, Option set 1` through `4, Modifiers, Display colour`. Selects `items` of kind `retro`, `sealed`, `accessory` or `other` that are `in_stock`, and either have never been exported (`sumup_synced_at` empty) or have changed since `since` (`updated >= since`); with `since` left off, only items never exported are selected. `Item name` is the item's own SKU **display form** (with its hyphen, `GGP-7F3K2Q`) followed by the title, so a SumUp sale can be matched back by eye and by `POST /api/vault/sumup/pull`'s own SKU-prefix matching rule below; `SKU` and `Barcode` carry the **encoded** form (no hyphen), or the item's EAN in `Barcode` for `sealed`/`accessory` when one is on file. `Tax rate (%)` is `0` for a margin-scheme item, the standard rate (a hardcoded 20, the same figure `sales.pb.js` already hardcodes for a standard-scheme sale line's own `vat_rate` - `settings` carries no separate field for it) for a standard-scheme item when `settings.vat_registered`, else `0`. Every row exported sets `items.sumup_synced_at` to the export's own timestamp, **unless** the request also carries `dry_run=1`, which builds the identical file but writes nothing, so a preview does not stop those rows appearing again on the next real export.

`GET /api/vault/exports/ebay-listings.csv?ids=<comma list>`

A listing file for the given `in_stock` items, ebay.co.uk in GBP - docs/csv-formats.md, "eBay listing export", for the full column list and why `Category` and `ConditionID` are always left blank (no reliable source for either; Card Uploader's own eBay export, documented above, already covers this shop's primary eBay listing path for singles - this route is for whatever else gets listed directly). An id that does not exist, or is not `in_stock`, is left out of the file rather than failing the whole export. Marks nothing on any item.

`GET /api/vault/exports/inventory.csv?status=&game=&kind=`

Every `items` row matching the given filters, all optional (`status` and `kind` are the collection's own enum values; `game` is a `games.key` such as `pokemon`, resolved to the relation internally - an unrecognised key matches nothing rather than erroring). Columns: docs/csv-formats.md, "Inventory export".

`GET /api/vault/exports/sales.csv?from=YYYY-MM-DD&to=YYYY-MM-DD`

One row per `sale_lines` row (via `lib/vaultutil.js`'s `saleLineRows`, so the line order matches every other place this codebase reads them) for every `sales` row created in the range. Columns: docs/csv-formats.md, "Sales export". Unlike the stock book, this is a plain listing, not a refund-aware breakdown: `Unit price` and `Discount` are the as-sold figures straight off the line, and `Sale total` is the sale's own `total` repeated on every one of its lines - a partially or fully refunded sale still shows what was originally sold, since the stock book (not this export) is the VAT/margin record that has to account for refunds.

`GET /api/vault/exports/buy-in-register.csv?from=YYYY-MM-DD&to=YYYY-MM-DD` (**admin**)

One row per accepted `trade_in_lines` row (seller snapshot included) for every `trade_ins` row `completed` in the range (by `completed_at`). Columns: docs/csv-formats.md, "Buy-in register export". `Payout type`, `Cash amount` and `Credit amount` are the whole trade-in's own figures, repeated on every line of it - a mixed payout is never split per line anywhere in the data model, so repeating the total is the honest figure rather than an invented split, the same reasoning the stock book already applies to its own purchase columns.

`GET /api/vault/exports/end-listings.csv`

Every `items` row with an `ebay_listing_id` **or an `ebay_sku`** whose `status` is `sold`, so those listings can be ended on eBay (there is no eBay write API in this build - Seller Hub or Card Uploader's own Managed Inventory ends the listing itself). The `ebay_sku`-alone case matters in practice: nothing in this build writes `ebay_listing_id` at all yet, so a Card-Uploader-listed item (which only ever carries its `CS-XXXXXX` `ebay_sku`) that is then sold at the counter, rather than through the eBay orders import, would otherwise never appear here even though its listing still needs ending. Columns: docs/csv-formats.md, "End-listings export". Marks nothing; `POST /api/vault/items/end-listings` below is the one route that clears an item off this list.

`POST /api/vault/items/end-listings`

Request: `{ "ids": ["<item id>", ...] }`. In one transaction, clears `ebay_listing_id` and `ebay_sku` on each item that has either set; an id that does not exist, or has neither, is silently skipped rather than failing the whole call. 400 with no `ids`.

Response 200: `{ "ended": ["<item id>", ...] }` - only the ids actually cleared.

### Imports

`POST /api/vault/imports/card-uploader` and `POST /api/vault/imports/ebay-orders` are both multipart: a `file` field (the CSV) and an optional `type` field (`"card_uploader"` or `"ebay_orders"`) that, when given, must match the route's own type - posting the wrong one is refused with 400 ("This is the Card Uploader import..." / "This is the eBay orders import...") rather than silently importing through the wrong mapping. Both carry `$apis.bodyLimit(10 MB)`, so an oversized request is refused before anything is even read off it, and both also refuse a file over 10 MB with a plain sentence once the body has been read (the in-handler check a multipart request's own framing overhead can still reach ahead of). Both refuse cleanly with **"That file is not a CSV we recognise. Check the first line has the column headings."** (400) when the header row resolves none of the mapping's own columns at all, or the file has no rows.

Both run the whole import - the `csv_imports` bookkeeping row and every `items`/`sales` write it makes - inside one `$app.runInTransaction`, so a file that fails partway through a **system** error leaves nothing behind: if even the bookkeeping row itself cannot be saved (the rare case), the whole call is refused with a plain 400 rather than a bare 500. A single bad *row* never aborts that transaction: name-only rows, unreadable prices, unknown custom labels and already-sold items are collected into the `csv_imports` row's own `errors` list instead, so the rest of the file still goes through.

**Mapping configs.** Neither importer has hard-coded headers: each reads `settings.import_mappings.card_uploader` / `.ebay_orders`, the same `{ headerRow, columns: { field: [header, header, ...] } }` shape docs/csv-formats.md already sketches, the first alias present in the header row winning per field. A Phase 4 migration seeds both with exactly that skeleton (`packages/shared` is not involved - this is plain settings data). **Richard confirms the real header names once a genuine Card Uploader and eBay orders export are in hand**, by editing `settings.import_mappings` directly (there is no dedicated route for it in this phase - it is an ordinary field on the already-admin-only `settings` collection); this file and docs/csv-formats.md record what the seeded default is and where to change it. A settings row with no `import_mappings` entry for a given importer (an install that predates the migration) falls back to the same skeleton hard-coded in `pb_hooks/lib/imports.js`, so an importer never simply refuses to run for want of a mapping.

`POST /api/vault/imports/card-uploader`

Card Uploader's per-card export (docs/csv-formats.md, "Card Uploader import"). A row carrying a `tcgplayerId` or `cardmarketId` matches a `cards` row directly (both are indexed); a row with only a `name` goes to the review list instead of guessing - an `errors` entry `{ "row": <1-based line number>, "kind": "review", "message": "needs match", "name": "...", ... }`.

Once a card is matched, in order:
1. **An existing item already carrying this file's `ebay_sku`** (its `CS-XXXXXX` custom label) is updated in place: `status: "listed_ebay"`, `price` and `qty` from the file, `condition` when the file gives one - **unless** that item's own `status` is `sold`, `returned` or `written_off`, in which case the row is reported rather than resurrecting a disposed item: `{ "row": ..., "kind": "already_sold", "message": "already sold", "ebay_sku": "..." }`.
2. **Failing that, the oldest still-`in_stock` item already linked to this exact card** (narrowed by `condition` when the file gives one, and by `finish`/`language` when the configured mapping itself maps those columns) is the same physical card already on the shelf - it is connected to the listing (`status`, `ebay_sku`, `price` set) with `cost`, `source`, `acquired_at`, `trade_in_line` and `location` left exactly as they are, so a card that came in through a trade-in or a supplier order is never duplicated just because it is now also being listed on eBay.
3. **Only when neither exists** is a brand new `items` row created: `kind: "single"`, `status: "listed_ebay"`, `price`/`qty`/`condition`/`ebay_sku` from the file, `source: "supplier"`, `tax_scheme: "margin"`, `acquired_at: now`, `location: settings.default_intake_location` when set, `created_by` the importing staff member. Its `cost` is left unset - a listing with nothing already in stock behind it - so alongside the create an `errors` entry is still added: `{ "row": ..., "kind": "review", "message": "Listed card was not in stock...", "card": "...", "sku": "..." }`, purely to make that zero cost visible on the review screen; the row still counts as `matched` (the item really was created), not `review`.

A row whose price does not read as an amount, or that carries neither an id nor a name, is a hard failure - `{ "row": ..., "kind": "error", "message": "..." }` - and is not counted in `rows_ok`. Every row's own writes run inside a try/catch of their own, so one row this build cannot write for an unexpected reason becomes an `error`-kind entry rather than aborting the rest of the file; `errors` itself is capped at its first 200 entries plus a final `{ "kind": "truncated", "count": <n omitted> }` when a file has more problems than that.

Response 200: `{ "import": <csv_imports row>, "matched": <n>, "review": <n> }`. `csv_imports.rows_ok` is `matched + review` - `review` counts only a row that could not be matched to any card at all, never the "matched but not in stock" case above (which is a `matched` row that also happens to carry a review-kind note), so the two never double-count the same row.

`POST /api/vault/imports/ebay-orders`

eBay's orders report (docs/csv-formats.md, "eBay orders import"). **One order is one sale**: every row sharing the same `orderNumber` is grouped into a single `sales` row (`channel: "ebay"`, `external_ref: orderNumber`, truncated to the field's own 100 characters) with one `sale_lines` row per row of the file - re-running an import that adds a later row to an order already on file finds that sale again by its `external_ref` and adds the new line to it, rather than creating a second sale for the same order. A row with no order number at all still gets a sale of its own, matching the plan's "record the order reference on the sale" for a file that never carries one.

`sales.occurred_at` is taken from the group's own `saleDate` column (its first row's value; every row of one order is presumed to share a date) and falls back to now when that cell does not parse as a date - see "Every sale carries `occurred_at`" below.

Each row within a group matches its own `customLabel` to an item's `ebay_sku`. An item already `sold`, `returned` or `written_off` is reported rather than sold again - `{ "row": ..., "kind": "already_sold", "message": "already sold", "custom_label": "..." }`. **Idempotency is not the item's status**, though: a `sale_lines` row already tying that item to this exact sale is what actually says a row was processed before, reported the same `already_sold` way - the item's own status alone cannot tell, since selling part of a multi-unit stock line (below) legitimately leaves it short of `sold`. This is what keeps re-running the same file, or a later export that overlaps an earlier one, from ever double-selling the same line of the same order.

A matched, not-already-processed row gets one `sale_lines` row at the file's sold price; the item's `qty` is decremented by the row's own quantity and its `status` is only set to `sold` once nothing is left (mirroring `sales.pb.js`'s own counter-sale logic) - a partial sale of a multi-unit stock line stays `listed_ebay` with its `qty` reduced, not falsely marked sold out. `payment` is left blank on every created sale: none of `sales.payment`'s values (`sumup_card`, `cash`, `store_credit`, `points`, `mixed`) describe money that went through this shop, since eBay collected the buyer's payment on its own side, and `channel` is what actually says how the sale happened.

An unmatched custom label, or an unreadable sale price, is a hard failure the same way as the Card Uploader importer's own, and every row's writes run inside their own try/catch the same way too - see that section above for the shared `errors` cap.

Response 200: `{ "import": <csv_imports row>, "sold": <n>, "already_sold": <n> }`. `rows_ok` is `sold` alone - an `already_sold` row changed nothing, so it does not count as a fresh success.

`GET /api/vault/imports/:id`

The `csv_imports` row as stored, `errors` included - the review screen reads this directly rather than a separate endpoint. 404 when the id does not exist. Audited (`action: "import_view"`, identifiers only), the same as every other route in this contract.

A "needs match" review entry (either branch above) also carries this row's own `price` (parsed to pence, or `null` when it did not read as an amount), `quantity`, `condition` and `ebay_sku` - whatever they parsed to, even blank - alongside the name/id fields a human matches by, so the manual link route below has everything the matching rule needs without re-reading the original file.

`POST /api/vault/imports/:id/link` (staff)

Resolves one "needs match" row from an import's own `errors` list by hand, for the counter screen's review queue - the alternative to creating an `items` row itself through the collection API, which would bypass the three-path rule above entirely and risk a duplicate, zero-cost item for a card already on the shelf. Body `{ "row": <the row's own 1-based line number>, "card": "<cards id>" }` links it, running the exact same three-path rule the automatic import uses (an existing item by this `ebay_sku`, with the same disposed-item guard; else the oldest `in_stock` item on that card, narrowed by `condition` when the row has one - never by `finish`/`language`, which the review entry does not carry; else a new `source: "supplier"` item); `{ "row": <n>, "skip": true }` dismisses it instead, without listing anything.

A successful link marks the item `listed_ebay` with the row's own `price` and `ebay_sku`, sets `created_by` and `location` exactly as the automatic import would on a genuinely new item, and drops the row's "needs match" entry from `errors` (`rows_ok` is left exactly as it was - the row already counted toward `review` when the file was first imported). When the three-path rule lands on "create a new item", the dropped entry is replaced with the same zero-cost review note the automatic import itself would have left (`{ "kind": "review", "message": "Listed card was not in stock. Created with no cost - check it.", "card": "...", "sku": "..." }`), so a manually-linked row that still had nothing in stock behind it stays just as visible for Richard to check as the automatic case is. A skip drops the entry outright and adds one to `csv_imports.rows_skipped` (a new field alongside `rows_total` and `rows_ok`).

Refusals: **404**, "That row is not waiting for a match." - the import id does not exist, or `row` carries no current "needs match" entry. **409**, "This row has already been linked or skipped." - `row` names a row this route has already resolved once (tracked in a new `csv_imports.resolved_rows`, separately from `errors`, precisely so a *second* attempt at an already-resolved row reads as this conflict rather than the same 404 as a row that was never there). **400** - no `row`, or neither `card` nor `skip`; `card` does not resolve to a `cards` row ("Card not found. Check the id."); or this row's own captured price did not parse at import time ("This row's price could not be read as an amount. Re-import the file with a valid price.") - link only, a skip never needs one. **409** again, "That listing has already sold, been returned or been written off." - a link whose `ebay_sku` happens to already tag an item disposed of since the file was first imported.

Response 200: `{ "import": <csv_imports row>, "item": <items row, or null for a skip>, "path": "ebay_sku" | "in_stock" | "created" | "skipped" }`. The lookup, the match, the `csv_imports` save and the audit row all run inside one `$app.runInTransaction`; audited as `import_link` with `row`, `card`, `item` and `path` only, never the row's own name, set or number.

**A staff token can no longer update a `csv_imports` row directly at all** (`csv_imports.updateRule`, a Phase 4 review-round migration): every field on it - `status`, `rows_ok`, `errors`, `resolved_rows`, `rows_skipped` included - is now written only by the three routes above, which run as `$app` or a transaction's `txApp` and so bypass collection API rules entirely, the same as every other hook-only write in this build. Only an admin can still update one directly, for the rare hand fix; listing and viewing a `csv_imports` row through the collection API are unaffected.

**`sales.channel` and `sales.external_ref`** (new fields, this phase's migration): `channel` is `"counter"` or `"ebay"`, `external_ref` is free text (the eBay order reference, truncated to 100 characters if the file's own is longer). A small `onRecordCreate` hook on `sales` in `pb_hooks/sales.pb.js` defaults an empty `channel` to `"counter"` and an empty `occurred_at` to now, so an ordinary counter sale carries both without the completion route knowing about them - the same pattern `items.pb.js` and `customers.pb.js` already use for a field a create call leaves blank.

**Every sale carries `occurred_at`** (a `sales.date` field added by a separate migration this phase, backfilled to `created` for every row that predates it): the date the sale actually happened, as distinct from `created`, which is only when the database row was written. For a counter sale the two are the same instant, filled in by the same `onRecordCreate` hook above when a create leaves it blank; for an eBay-orders-imported sale they can genuinely differ - a file imported on a Friday covering a week of orders books each sale on its own order date, not on the Friday the import ran. Every report and every `daily_stats` row groups, filters and ranges sales on `occurred_at`, never `created`.

**`items.created_by` and `sales.staff`** are set from the importing staff member on a row this phase actually creates (a brand-new Card Uploader item with nothing already in stock behind it; a new eBay-orders sale) - never on a row it only updates, since that would misattribute who actually brought a piece of stock in or rang up a sale that in truth happened on eBay, not at the counter.

### SumUp

`pb_hooks/adapters/sumup.js` follows the same shape as every other adapter (`adapters/http.js`'s own header comment): plain functions, `transport` always last and optional, so `pb_hooks/adapters/fixture_transport.js` can serve `GG_ADAPTER_TRANSPORT_MODE=fixture` calls for it exactly as it already does for eBay, IGDB and PriceCharting. It calls `GET /v2.1/merchants/{code}/transactions/history?changes_since=<iso>&limit=100`, follows the response's own `links` for paging, and calls `GET /v2.1/merchants/{code}/transactions?id=<id>` per transaction for its `products[]` (absent from the history list). Authentication is a plain `Authorization: Bearer <key>` - a SumUp merchant API key is a long-lived personal access token from the merchant's own dashboard, not an OAuth client-credentials grant, so unlike `adapters/ebay.js` and `adapters/igdb.js` there is no token to fetch or cache. The key lives at `settings.api_keys.sumup` (merged into the existing `api_keys` blob, matching every other provider's key already there) and the merchant code at `settings.sumup.merchant_code` - both seeded (empty) by this phase's migration. Neither leaves the server: `api_keys` is already dropped wholesale by name from `GET /api/vault/config`, and `sumup.merchant_code` is not a key or secret, so it is fine for an ordinary staff member to see it there.

`POST /api/vault/sumup/pull` (**admin**)

Fetches every transaction changed since the last pull (or the last 24 hours, on a first run with nothing stored yet), upserts `sumup_transactions` by `sumup_id`, and matches each newly-seen, `SUCCESSFUL`, non-refund one to a sale. With no API key or merchant code configured, returns `{ "fetched": 0, "matched": 0, "unmatched": 0, "refunded": 0 }` rather than an error - the hourly cron below runs on every install, configured or not.

**Every transaction is stored, whatever its status.** Only a `status: "SUCCESSFUL"` transaction that is not a refund is ever matched or counted in `matched`/`unmatched`:
- A **refund** (a negative `amount`, or SumUp's own refund type on the transaction) is stored and counted separately, in `refunded` - it is money going back to a customer, not a sale we made, so it is never attempted against either matching rule below.
- Anything else that is not `SUCCESSFUL` (`FAILED`, `PENDING`, ...) is stored but contributes to none of `matched`, `unmatched` or `refunded`.
- An **amount that cannot be parsed at all** is stored with `status` overwritten to `AMOUNT_UNREADABLE` (never left as whatever SumUp sent, and never silently treated as zero, which would risk a false match against a genuine zero-value transaction) and is likewise never matched, counted or included in `reconcile`'s totals; the transaction's own id is logged.

**Matching (a `SUCCESSFUL`, non-refund transaction only), in order:**
1. A `products[]` entry whose `name` starts with one of our own SKUs (exactly the form `GET /api/vault/exports/sumup.csv` writes into `Item name` - the display form, hyphen included, or the encoded form, either parses) - the item it names is looked up directly (`items.sku`), then the sale (not already claimed by another transaction) whose line for that item lands closest to the transaction's own `timestamp` - not simply the most recent one, so an item sold more than once still resolves to the sale a given transaction actually belongs to.
2. Failing that, a `sales` row with `payment` `sumup_card` or `mixed`, created within **three minutes** of the transaction's own `timestamp`, whose **card share** equals the transaction's amount, not already matched to another transaction. The card share is `total` for a plain `sumup_card` sale, but `payment_split.sumup_card` for a `mixed` one (`sales.pb.js`'s own `payment_split` shape) - a mixed sale's `total` also includes whatever was paid by cash, store credit or points, none of which ever reached SumUp, so comparing against `total` there would never match a genuine mixed-payment sale.

A transaction that already carries a `matched_sale` from an earlier pull is left alone for matching - only its other fields (`amount`, `status`, `fetched_at`, ...) refresh, `products` included whenever detail is actually re-fetched. Detail (`products[]`, the only source of it - absent from the history list) is fetched only for a transaction not already matched, and at most 100 times per pull; a pull with more new/unmatched transactions than that leaves the rest for the next one rather than making an unbounded number of calls. `sumup_transactions.amount` is parsed from SumUp's own decimal amount through the shared money helpers (`pb_hooks/lib/shared/money.js`) - taken as a string when SumUp already sends one, and only stringified from a number as the fallback, so a value that arrived as a proper decimal string is never round-tripped through a float first.

Response 200: `{ "fetched": <n>, "matched": <n>, "unmatched": <n>, "refunded": <n> }` - counts for this pull alone (an already-matched transaction seen again still counts as `matched`; `matched + unmatched + refunded` can be less than `fetched` when this pull also saw a `FAILED`/`PENDING` or amount-unreadable transaction, which contributes to none of the three).

`changes_since` is sent as a genuine ISO 8601 instant, kept in `adapter_state` (`adapters/statestore.js`) as its own marker rather than read back off `sumup_transactions.fetched_at` - that field is a PocketBase "date" field whose own stored text uses a space where ISO 8601 wants a "T", which SumUp's API cannot parse; every pull after the first was previously sending it a value SumUp would silently reject.

Also runs hourly, `:15` past the hour from 08:00 to 22:00 UTC (`pb_hooks/crons_sumup.pb.js`, `cronAdd("sumup_pull", "15 8-22 * * *", ...)` - a few minutes after the hour so a sale rung through moments ago has settled on SumUp's side, and only during trading hours). Kept out of `pb_hooks/crons.pb.js` (another package's file this round) as its own small file, the same shape as every existing `cronAdd` there.

`GET /api/vault/sumup/reconcile?date=YYYY-MM-DD` (staff)

The day's `sumup_transactions` (by `timestamp`) beside the day's card sales (`sales` with `payment` `sumup_card` or `mixed`, by `created`), for the Cash screen. Only `status: "SUCCESSFUL"` transactions are ever included here - a stored `FAILED`, refund-bucketed or amount-unreadable row (see the pull route above) is left out of every list and every total, the same reasoning that keeps it out of `matched`/`unmatched` on the pull itself.

Response 200
```json
{
  "date": "2026-09-20",
  "matched": [
    { "transaction": { "id": "...", "sumup_id": "...", "transaction_code": "...", "amount": 1999, "timestamp": "...", "status": "SUCCESSFUL" }, "sale": { "id": "...", "number": "GG-S-000123", "total": 1999, "card_share": 1999 } }
  ],
  "unmatched_transactions": [ { "id": "...", "sumup_id": "...", "transaction_code": "...", "amount": 500, "timestamp": "...", "status": "SUCCESSFUL" } ],
  "unmatched_sales": [ { "id": "...", "number": "GG-S-000124", "total": 2000, "card_share": 500, "payment": "mixed", "created": "..." } ],
  "totals": { "sumup": 2499, "sales": 2499, "difference": 0 }
}
```
`card_share` (on every `matched[].sale` and `unmatched_sales[]` row) and `totals.sales` are the same figure the pull's own matching rule 2 compares against - `total` for a plain `sumup_card` sale, `payment_split.sumup_card` for a `mixed` one - not `sales.total` itself, which the second `unmatched_sales` example above deliberately shows diverging from (a £20 mixed sale with £5 on card still contributes only 500 to `totals.sales`, never 2000). `totals.sumup` is the day's own `SUCCESSFUL` transaction amounts, matched or not; `difference` is `sumup - sales`. 400 with no `date`, or one that is not shaped `YYYY-MM-DD` **or is not a real calendar date** (`lib/csv.js`'s own `isValidDateStr` - "2026-13-45" is shaped right and still refused, rather than reaching an Invalid Date downstream and answering with a bare 500).

**A manual match, for one of reconcile's own `unmatched_transactions`/`unmatched_sales` pairs, is a plain `PATCH /api/collections/sumup_transactions/:id` with `{ "matched_sale": "..." }`** - there is no dedicated route for it, since there is nothing beyond the one field to write. This is now the *only* thing a staff PATCH to `sumup_transactions` may do: `sumup_transactions.updateRule` (a Phase 4 review-round migration) requires every other field (`sumup_id`, `transaction_code`, `timestamp`, `amount`, `payment_type`, `status`, `products`, `fetched_at`) to be absent from the request body, the same `@request.body.<field>:isset = false` pattern `stock_counts.status` already uses, so a staff member cannot rewrite a transaction's own amount or status to manufacture a reconcile figure that never happened. An admin is unrestricted. The pull and reconcile routes themselves are unaffected either way - both run as `$app`, which bypasses collection API rules entirely, the same as every hook-only write in this build.

### Implementation notes (as built in Phase 4)

- **`GET /api/vault/exports/sumup.csv`'s `since` filter is additive, not exclusive**: an item never exported appears regardless of `since` (it has to reach SumUp at least once), and `since` only widens the set to items that have also *changed* since then. Leaving `since` off is therefore the narrowest call (never-exported items only), not the widest.
- **The `Item name` display-form SKU and the `SKU`/`Barcode` encoded-form SKU are deliberately different strings on the same row** - `pb_hooks/lib/shared/sku.js`'s `displayCode`/the record's own stored (encoded) value - matching docs/csv-formats.md's worked example exactly. `POST /api/vault/sumup/pull`'s SKU-matching rule accepts either, since `sku.parseCode` normalises a hyphen away before validating.
- **`lib/csv.js` is the one place every Phase 4 route builds or reads a CSV through** - `row()`/`cell()`/`pounds()` wrap `lib/vaultutil.js`'s own `csvRow`/`csvCell`/`poundsCell` rather than duplicating the escaping rule, and `parse()`/`mapRows()` are the shared reader every importer's mapping resolves through. `queryParam()`/`dateParam()` live here too, not in `lib/vaultutil.js`: a `routerAdd` handler cannot see a plain function declared at the top of its own `.pb.js` file (pb/README.md's hook-isolation rule), and `exports.pb.js` now registers six such handlers that all need one.
- **The eBay listing export's `Category` and `ConditionID` columns are always blank on purpose.** There is no eBay File Exchange export on hand to check a real column set against, and no reliable source in this build for either an eBay category id or an eBay condition id - Seller Hub's own matching is more reliable than a guess from `games`/`kind`/`condition`. Confirm the wider column set against a real eBay bulk-listing template once Richard has one, the same "confirm once a real export exists" caveat as the Card Uploader and eBay orders mappings.
- **A refund is not reflected in `sales.csv`.** It is a plain listing of what was sold, at the as-sold figures - the stock book (`GET /api/vault/exports/stock-book`, Phase 2) is the one export that already accounts for refunds, and duplicating that accounting here would risk the two disagreeing. (A SumUp *transaction* refund - money going back through the card reader - is a different thing again: see the pull route's own refund bucket above.)
- **The SumUp pull writes one `audit_log` row per call, not per transaction** (`action: "sumup_pull"`, `meta: { since, fetched, matched, unmatched, refunded }`), the same way a bulk export audits its own filters and row count rather than one row per CSV line.
- **Every audit row this package writes holds counts and, at most, the first 20 ids - never a whole array of them.** `export_ebay_listings_csv` and `end_ebay_listings` in particular could otherwise be handed a very large `ids` list straight from the request; their `meta` carries `id_count` (the true total) alongside `ids` (capped at 20), the same shape `csv_imports.errors` itself is capped at 200 entries plus a `truncated` marker for the same reason - a permanent, superuser-only table gaining an unbounded value from ordinary use is worth avoiding on its own terms, separately from the PII reasoning that already keeps audit meta to identifiers.
- **`GET /api/vault/imports/:id` writes `import_view`, an ordinary read-route audit row** (identifiers only) - the exception CLAUDE.md's contract convention already allows for a route "every counter screen loads" (`GET /api/vault/config`, the id-document lookup) does not apply here, since this is a deliberate look at one specific import's own detail, not a routine load.
- **A `links[].next` href is only followed onto SumUp's own origin.** A relative, path-absolute href (`/v2.1/...`) is resolved against `https://api.sumup.com`; anything that would leave that origin, or is not a usable string at all, simply stops paging rather than being followed - `adapters/sumup.js`'s own `resolveNextUrl`, unit-tested in `pb/scripts/check-adapters.mjs`.
- **The "already claimed" sale-id lookup a pull uses to stop either matching rule double-booking one sale is itself bounded to a recent window** (the three-minute match window plus an hour's margin either side of the pull's own `since`), not every `sumup_transactions` row this shop has ever matched - a transaction from months ago could never be a candidate for either rule anyway, both of which are themselves bounded to within three minutes of the transaction under consideration, so this changes nothing about which sale a transaction matches, only how much history a pull has to load to find out.
- **Every Phase 4 fixture used by `pb/scripts/check.sh` is hand-written** (`pb_hooks/adapters/fixtures/sumup_HANDWRITTEN_*.json`), the same as eBay's, IGDB's and PriceCharting's own - nobody on this build has a SumUp merchant account to record a real response from. Two of the five fixture transactions (the amount-and-time match, and the mixed-payment one) carry a `timestamp` of the literal string `"__NOW__"`, resolved to the real current instant by `fixture_transport.js` itself the moment it is served: a transaction meant to be matched by amount and a three-minute time window cannot be tested against a timestamp fixed at fixture-authoring time, since that will essentially never fall within three minutes of whatever wall-clock second a real test run reaches it at. Only that one field is ever a placeholder; every fixture's shape is otherwise the real, documented response shape.
- **`lib/imports.js`'s three-path matching rule is one function, `applyCardMatch`, called from two places**: the automatic `processCardUploaderRows` loop, and `resolveReviewRow` behind `POST /api/vault/imports/:id/link`. This is the fix for the counter screen's own review queue having drifted from the rule by creating `items` rows itself through the collection API - a manual link and an automatic match can no longer disagree about what "already in stock" or "already sold" means, because they run the identical code. `resolveReviewRow` mutates the `csv_imports` record it is handed (`errors`, `resolved_rows`, `rows_skipped`) but never saves it - the route saves once, inside its own transaction, alongside the audit row, so a link is all-or-nothing the same way the two POST import routes already are.
- **`csv_imports.resolved_rows` exists only to tell "never was a review row" apart from "was, and got resolved"** once a row's `errors` entry has actually been dropped (`POST /api/vault/imports/:id/link`'s own 404 versus 409). It is a small, staff-click-driven array, never touched by the file import itself, so it is not capped the way `errors` and audit `ids` are - realistically it never approaches a size where that would matter.

## Phase 5: portal, quotes, want lists, estimate and notifications

The customer portal's own routes, the remote quote lifecycle, want lists with holds, the two public estimate routes, and how a notification actually reaches someone. Conventions are as above: money is integer GBP pence, dates ISO 8601. Two new token types appear in this section's own column: **customer** (a `customers` token, `$apis.requireAuth("customers")`) and **public** (no token at all - PocketBase still resolves `e.auth` from a bearer token if one is sent, but a public route never requires one and the two estimate routes never read it). Every write route in this section is audited (identifiers only, per CLAUDE.md); a route audited as a customer's own action carries that customer's own id as `actor`, the same way a staff action carries the staff id.

Beyond this phase's own new routes, the portal also reads several Phase 1/2 collections directly through the collection API with its own customer token, under rules that already existed and are unchanged here: **`trade_ins`** and **`credit_ledger`**/**`points_ledger`** (`customer = @request.auth.id`, alongside staff), and **`trade_in_lines`** (`trade_in.customer = @request.auth.id`, a relation lookup, since the line itself carries no `customer` field of its own). A customer token can list and view their own rows in all four and never another customer's (a cross-customer view 404s or 403s, per the same PocketBase list-vs-view distinction `pb/README.md`'s "API rules" section already describes); `pb/scripts/check.sh` section 23 asserts both directions for each.

### `GET` / `PATCH /api/vault/me`

One registration, not two: `pb_hooks/routes.pb.js` already owned `GET /api/vault/me` for staff (their own hand-picked fields) before this phase, and PocketBase's router refuses a second handler on the same method and path outright. The customer branch was added to that same handler rather than registered again in `portal.pb.js` - `e.auth.collection().name` decides which shape comes back. Both branches need `$apis.requireAuth("staff", "customers")`.

customer shape (`lib/vaultutil.js`'s `meShapeFor`, the one place `GET /me`, `PATCH /me` and `GET /c/:token` all build it):

```json
{
  "customer": {
    "id": "...", "code": "GGC7F3K2Q", "name": "...", "email": "...", "phone": "...",
    "marketing_consent": false, "birthday_month": 9, "qr_token": "...", "created": "...",
    "notifications": { "email": true, "push": true }
  },
  "balances": { "credit": 1000, "points": 300 },
  "tier": { "id": "...", "name": "Regular" } | null,
  "id_status": "none" | "verified" | "expired" | "rejected",
  "push": { "vapid_public_key": "" },
  "counts": { "trade_ins": 2, "open_quotes": 1, "want_list": 1 }
}
```

`push.vapid_public_key` (fix round, finding 2) is the same field `GET /api/vault/config` already carries, added here too: `/config` is staff-only, so it was the only place a customer's own portal could ever have read this from, meaning push could never actually be turned on there. `/config` itself is unchanged and stays staff-only - this is additive, not a widening of that route.

`balances` is always summed live from `credit_ledger`/`points_ledger` (`lib/balances.js`'s `creditBalance`/`pointsBalance`, not `.recompute`, which also writes - a `GET` never does), never `customer_private`'s cached fields. `tier`/`id_status` are the only two things read off `customer_private`; nothing else on that record ever reaches a customer route. `counts.trade_ins` is every trade-in the customer has (any status); `counts.open_quotes` is `submitted`, `reviewing`, `offered`, `accepted` or `received` (not `declined`/`expired`/`completed`); `counts.want_list` is `open` or `matched` (not `closed`/`fulfilled`) - none of this is specified further than the field names in the brief this package was built against, so these are the counting rules actually shipped.

`customer.notifications` and `PATCH`'s `notifications: { email, push }` body field are an addition beyond the literal contract: the brief's `PATCH /me` accepts a `notifications` preference but the shape list gives it nowhere to be read back from. `customers.notify_email` / `.notify_push` (new columns, default `true`, set on every customer by this phase's migration and by `customers.pb.js`'s own create hook from then on) hold it; `lib/notify.js` skips emailing a customer whose `notify_email` is `false`, and `services/notify` skips pushing to one whose `notify_push` is `false`. Nothing else in the `/me` shape is invented.

`PATCH /api/vault/me` accepts any of `name`, `phone`, `marketing_consent`, `birthday_month`, `notifications: { email, push }` and returns the same shape as `GET`. `email` in the body is refused outright with 400 "Email cannot be changed here. Ask a member of staff to update it." - the brief's own reasoning (email is the sign-in identity) is treated as a hard refusal rather than a silently-ignored field, so a client learns its request was not applied rather than assuming it was. Audited as `customer_self_update`, meta `{ changed: [...field names...] }`, never a value.

### `GET /api/vault/me/export`

A JSON download (`Content-Disposition: attachment; filename="gg-vault-export-<code>.json"`) of: the customer's own record (id, code, name, email, phone, created), `consent.marketing_consent`, `id_status` alone (never an ID field), every trade-in with its lines, every sale linked to the customer (number, `occurred_at`, total, payment, status - no other customer's data, trivially true since every query filters on `customer = <this id>`), both ledgers in full, every quote **without its `photos` field**, the want list, and notifications. Phase 6 adds the Guild to the same download (`guild`, `vouchers`, `memberships`, `perk_usage`, `referrals`); see that section for the shapes and for what a referral deliberately does not carry. Audited: `customer_self_export`, meta a row count per section, never the export's own contents.

### `POST /api/vault/me/delete`

The same erasure `POST /api/vault/customers/:id/erase` performs, factored into `lib/customerops.js`'s `erase(app, customerId, opts)` so the two routes cannot drift: both callers pre-check the credit balance for the fast, "validate first" refusal, then call `erase` again inside their own transaction for the re-check that has to be atomic, passing their own audience-appropriate wording (`opts.creditRefusal`) - staff sees "This customer still has ...", the customer themself sees "You still have ... store credit. Use it or ask the shop to pay it out first." `erase` now also calls `customer.setRandomPassword()`, rotating the auth record's `tokenKey` (the same mechanism `lib/stepup.js`'s own doc comment describes for a staff password change) - every token issued to that customer before the erasure, portal or otherwise, stops verifying the instant it commits, which is what "the token no longer works" in the brief means in practice. Response `{ "erased": true }`. Audited as `customer_self_delete`, same `meta.removed` shape as the admin route.

### `GET /api/vault/c/:token`

Public. No `qr_token` match: 404 "Not found." (never distinguishing "no such token" from anything else, and never a name). A match with no auth, or an auth that is neither staff nor that same customer: `{ "known": true }`. Staff: `{ "customer_id", "code", "name" }`. The owning customer: `{ "customer": <the /me shape above> }` - a literal reading of the brief's "gets `{ customer: <the /me shape> }`", so the response is a `customer` key whose value is itself the whole `/me` object (which has its own nested `customer` key) - double-nested on purpose, not a mistake, because that is what the contract says.

### Quotes

`quotes.createRule` is staff-only, as the brief's own migration list describes ("customers submit through the route"). An earlier build of this package left it at the Phase 2 expression (staff, or a customer creating their own row) to avoid touching `pb/scripts/check.sh` section 8's own direct-create assertion; a fix-round review found the real cost of that choice - a customer's own token could create a `quotes` row with any `status`, `lines` and `offer_total` it liked, which `POST /:id/received` then copied into a draft trade-in exactly as given and completion paid out, so a forged `accepted` row with priced lines was a genuine path to money, not just a shape mismatch. `createRule` is now tightened; section 8's own assertion was updated to expect the 400 PocketBase's own record-create endpoint gives for a failed createRule (not the 403/404 a failed list/view rule gives). `POST /api/vault/quotes` (below) is the only way a customer submits one; the `customer = @request.auth.id` update-rule carve-out (replying, accepting, declining their own quote) is untouched.

`POST /api/vault/quotes` (customer, multipart): `photos` (1-20 files, JPEG/PNG/WebP, 10 MB each, sniffed from the first bytes the same way `idphotos.pb.js` sniffs an ID photo - a client-declared content type or file extension is never trusted), `message` (≤4000), `drop_off` (`in_store` | `post`, defaults to `in_store`). Every accepted photo is re-wrapped through `$filesystem.fileFromBytes` from the bytes this route itself read and sniffed, never the raw multipart upload object, so what is actually stored is provably the sniffed image and nothing else. Creates the quote `submitted`, notifies every active admin (one `notifications` row each, emailed). Response `{ "quote": {...} }`. 400 "Photo *n* is not a JPEG, PNG or WebP image. Choose photos and try again." for a non-image; the same wording, by index, for an oversized one.

`GET /api/vault/quotes` (customer): `{ "quotes": [{ id, status, message, offer_total, offer_expires_at, drop_off, closed_at, created, updated }] }`, the caller's own quotes, newest first, capped at 50 - no photos or lines (use the detail route for those). Additive: `GET /api/collections/quotes/records?filter=customer=<id>` still works exactly as it did, under the collection's own unchanged rule; this route exists so the portal has one to call rather than building that filter itself.

`GET /api/vault/quotes/:id` (customer own, or staff): `{ quote, messages: [{ id, author: "customer"|"staff", body, created }], photos: [{ name, url }] }`, `messages` oldest first. `photos[].url` carries a file token minted from the caller's own auth record (`e.auth.newFileToken()` - works for a customer token exactly as it does for staff, both being auth-collection records; `quotes.photos` is `protected`, so the bare path 404s). A customer who does not own the quote gets 404, not 403 - the same "never confirm another customer's record exists" reasoning as `GET /c/:token`'s unknown-token case.

`POST /api/vault/quotes/:id/messages` (customer own, or staff): `{ "body": "..." }` (≤2000). Response `{ "message": { id, author, body, created } }`. The other side is notified: staff message → the customer, email and push (`notify_email` permitting); customer message → every active admin, a notification row each, **not** emailed (the brief's own distinction: quote submission says "emailed", a reply from the customer does not).

`POST /api/vault/quotes/:id/offer` (staff): `{ "lines": [{ card?, retro_title?, title, condition?, finish?, qty, market_price, market_source, offer_price }], "message"? }`. `offer_total` is `Σ offer_price × qty`, recomputed from the submitted lines every time - nothing about a client-sent total is ever read. Sets `lines`, `offer_total`, `offer_expires_at` (now + `settings.quote_expiry_days`, falling back to 14 days for an unseeded settings row), status `offered`. An optional `message` becomes a `quote_messages` row (`author_kind: "staff"`) in the same transaction, so a covering note rides along with the offer itself. Notifies the customer, email and push, subject `"Your quote offer, £<total>"`. 409 unless the quote is `submitted` or `reviewing`.

`POST /api/vault/quotes/:id/reviewing` (staff): `submitted` → `reviewing` only; 409 from any other status.

`POST /api/vault/quotes/:id/accept` / `/decline` (customer own): `{ reply?, drop_off? }`. Only from `offered`, and only before `offer_expires_at` - past it, 409 `"This offer expired on <D MMM YYYY>. Ask for a new one."` (the short UK date form, `lib/quotes.js`'s `ukDateShort` - "27 Sep 2026", not `lib/receipts.js`'s full-month `ukDate`). Every active admin is notified with a row (not emailed - staff already watch the quote queue). Two independent route registrations, not one shared by a small factory function that closes over `targetStatus`/`actionName`: a closure captured by an outer function is not guaranteed to survive into the isolated context a handler actually runs in at request time, the same reasoning a bare top-level `const` does not (pb/README.md) - this was hit and fixed during this build (see the report), so the accept and decline handlers are two near-identical, fully self-contained bodies on purpose.

`POST /api/vault/quotes/:id/received` (staff): only from `accepted`. Creates a `trade_ins` row (`channel: "remote"`, `status: "draft"`, `quote` set, the customer) and one `trade_in_lines` row per quote line (`market_currency: "GBP"` throughout - the quote's own lines carry no currency or fx_rate, since a remote quote is priced by staff against a UK figure directly; `accepted: true` on every line, since a quote's lines are exactly what was offered and accepted), marks the quote `received`. Response `{ "trade_in_id": "...", "number": "" }` - `number` reads back empty on purpose: a draft trade-in has none yet (`pb/README.md`, "`trade_ins.number` starts life empty"), and this route does not invent one early. Completing that trade-in through the unmodified Phase 2 route (`pb_hooks/tradeins.pb.js`) assigns the real number as always.

A `trade_ins` `onRecordUpdate` hook in `quotes.pb.js` (the one small hook this package adds beside a Phase 2 collection, per this brief's own allowance - `tradeins.pb.js` itself is untouched) marks a linked quote `completed` the moment that trade-in's own `status` first becomes `completed`.

`POST /api/vault/quotes/:id/cancel` (staff): `{ "note": "..." }` (required, 400 without one). From any status **except** `declined`, `expired`, `completed` or `received` (a quote already converted to a trade-in is not "cancelled" back), to `declined`, with the note landing as a `quote_messages` row (`author_kind: "staff"`). Beyond the brief's own wording, the customer is also notified (email and push, body the staff note) - the same courtesy a customer's own decline extends to staff, offered back the other way; this is the one behavioural addition in this section that is not directly asked for, noted here and in the report rather than left silent.

`quotes.closed_at` (new column) is stamped by its own small `onRecordUpdate` hook in `quotes.pb.js` the moment `status` first reaches `completed`, `declined` or `expired`, from *any* route or cron that gets it there - the same shape as `items.pb.js`'s own `listed_at` hook. This is what the `quote_photos_retention` cron (nightly, 90 days) reads, rather than `updated`, which a later message or reply would otherwise push forward and delay the purge (`pb/README.md`'s Phase 4 retention section flagged exactly this gap; this closes it).

`quote_messages` (new collection): `quote`, `author_kind` (`customer` | `staff`), `customer`, `staff`, `body` (≤2000). Staff have full access; a customer may list, view and create on their own quote only (their own `customer` id and `author_kind: "customer"`, and never a `staff` value on the row), never update or delete - append-only, the same reasoning the ledgers are.

Cron `quotes_expire` (hourly, `0 * * * *`): every `offered` quote past `offer_expires_at` becomes `expired` and the customer is notified (email and push). A quote due within 24 hours gets one `quote_expiring` notification, guarded against a duplicate by checking whether one already exists for that quote (`link: "/account/quotes/:id"`) rather than by a separate "warned" flag on the row.

Cron `quote_photos_retention` (nightly, `30 3 * * *`): every quote closed (see `closed_at` above) at least 90 days ago with photos still on it has them cleared (`photos: []`) - the record itself, and every other field, stays.

### Want lists

`POST /api/vault/want-list` (customer): `{ card?, free_text?, max_price? }` - one of `card` or `free_text` is required. Creates `status: "open"`. Response `{ "row": { id, card: { id, name, set, number, image } | null, free_text, max_price, status, matched_item, notified_at, created, hold } }` - `card` is expanded from the bare relation id into its name/set/number/image (`lib/wants.js`'s `wantRowShape`, the same name/set/number/image shape the public estimate route already returns a card as) so the portal has a title and a picture to show without a follow-up request; `null` for a free-text row. `hold` is always `null` here (a row is never born matched); see the list route below for when it is not.

`GET /api/vault/want-list` (customer, own rows): added after the portal review below. `{ "rows": [{...}] }`, the same expanded shape as `POST` above, newest first, capped at 50. Additive, the same reasoning `GET /api/vault/quotes` documents: `GET /api/collections/want_list/records?filter=customer=<id>` still works under its own unchanged rule, but it can only ever return the bare `matched_item` id, because `items` is staff-only and a customer token has no rule letting it read that collection at all. This route resolves it at read time instead: `hold: { until, price, title }` (`items.reserved_until`, `.price`, `.title` on the matched item) while `status` is `matched`, `null` for an `open`, `closed` or `fulfilled` row (a released hold already cleared the item's own `reserved_until`, and a fulfilled one is sold, so there is nothing left to report as held either way).

`POST /api/vault/want-list/:id/close` (customer own): 404 for anyone else's row (never confirms it exists). Sets `status: "closed"`, response `{ "row": {...} }` in the same expanded shape. The `want_list.updateRule` also gained a matching customer-own carve-out (this phase's migration) so the same close can be done directly through the collection API, not only through the route.

The matching, fulfilment and release logic lives in `lib/wants.js`, driven by two `items` hooks in `wants.pb.js` (separate registrations from `items.pb.js`'s own, which is untouched) and the `holds_release` cron:

- **On item creation, and on any update that makes `status` newly `in_stock`** (returning from `reserved`, `listed_ebay`, anything): the oldest (`sort: "created"`) `open` want-list row for the same `card` whose `max_price` is `0` (empty) or at least the item's own `price` takes it - `status: "reserved"`, `reserved_for` the customer, `reserved_until` now + `settings.holds.hours` (new settings field, default 48). The want row becomes `matched`, `matched_item` set, `notified_at` stamped, and the customer is notified email and push: `"<item title> is in. Held for you until <D Mon, HH:MM>."` (`lib/wants.js`'s `ukDateTime`), `link: "/account/wants"`. Only a `card`-linked want row is ever matched automatically; `free_text` rows wait for a member of staff.
- **On a reserved item becoming `sold`** (the Phase 2 sale route, unmodified, already refuses to sell a reserved item to anyone but `reserved_for`, so this only ever fires for the right customer): the matching `want_list` row (`status: "matched"`, `matched_item` = this item) becomes `fulfilled`.
- **`holds_release`** (every 15 minutes, `*/15 * * * *`): every `reserved` item whose `reserved_until` has passed goes back to `in_stock` (which, through the hook above, immediately tries the next oldest open want row for that card - a deliberate cascade, not a side effect to guard against) and clears `reserved_for`/`reserved_until`; its own `want_list` row (if still `matched`) becomes `closed`; the customer is notified email and push, `"Hold released"` / `"The hold on <title> has ended, so it is back on the shelf. Ask at the counter if you would still like it."`, `link: "/account/wants"`.

`settings.holds` (new, `{ "hours": 48 }`) is this figure's one home, read by `lib/wants.js`'s `holdHours`, matching how `settings.offer.ebayHaircutPct` is the eBay haircut's one home.

### Public estimate

`GET /api/vault/estimate/search?q=` and `GET /api/vault/estimate?card=<id>&condition=NM&finish=normal` - both public (no `$apis.requireAuth` at all; a bearer token, if sent, is simply never read), rate limited (below), no writes, and **never call an adapter or `registry.js`'s set-sync machinery** - even `resolveSetNumberQuery`'s own inline set-sync bootstrap (Phase 3) is avoided on purpose, since that can itself call an adapter on an install with no cached sets yet for a game, which a public, unauthenticated route must never risk. `lib/estimate.js`'s `searchCatalogue` instead matches only what is already in `cards`/`card_sets`: a `"<set token> <number>"` two-word query against `set.code ~ … || set.name ~ …` plus an exact `number`, falling back to a plain `search_text`/`name` search, capped at 8 rows either way.

`estimate/search` response: `{ "cards": [{ id, name, set, number, image, finishes }] }` - `set` is the set's own name (not its code, and not the `set_code`/`set_name` pair `GET /api/vault/lookup` returns), matching the shape list's own `card: { name, set, number, image }` for the second route. `finishes` is the card's own `finishes_available` (`adapters/storage.js`'s field, populated by a set sync when an adapter reports more than one finish for a card), `[]` when it was never set - added after the portal review below, so the estimate page can offer finish chips straight from a search hit rather than a follow-up request.

`estimate` response: `{ "card": { name, set, number, image }, "market": <pence>|null, "as_of": "..."|null, "cash": { "low", "high" }, "credit": { "low", "high" }, "note": "Subject to inspection in the shop." }`, read from cached `price_snapshots` (`adapters/pricing_policy.js`'s own `snapshotsFor`/`choose`, the identical machinery `GET /api/vault/cards/:id/prices` uses) and priced through the shared `computeOffer` (`lib/shared/pricing.js`) against the live `pricing_rules` and `settings.offer`/`condition_multipliers` - never a new formula. `high` is the offer at the requested `condition`; `low` is the offer one grade down (`lib/estimate.js`'s `oneGradeLower`; DMG has no lower grade, so `low` equals `high` at DMG). **When there is no cached price at all**, `market`/`as_of` are `null` and both bands are `{ "low": null, "high": null }` - an honest "no estimate yet" rather than a fabricated zero; not explicitly specified by the shape list, called out here as the implementation's own choice. 404 `"Card not found. Search again or visit the shop for a look in person."` for an unresolved `card` id; 400 for a bad `condition`, the same wording `prices.pb.js` already uses.

### Push

`POST /api/vault/push/subscribe` (customer or staff): `{ endpoint, keys: { p256dh, auth } }`, upserted by `endpoint` (a second subscribe with the same endpoint updates the one row rather than creating a second). `DELETE /api/vault/push/subscribe`: `{ endpoint }`. Neither route, nor its audit row, ever logs the endpoint or the keys - both are treated as credentials, the same reasoning `services/notify` itself never logs one. `GET /api/vault/config` gains `push: { "vapid_public_key": "" }` - `config.pb.js`'s existing `DROPPED` settings filter already stripped any field literally named `push` from the generic `settings` passthrough, so the public key is named back in as its own top-level key rather than exposed as `settings.push` (which would also have exposed nothing, since it stays dropped); the private half of the VAPID keypair never touches this collection or this route at all - it lives only in `services/notify`'s own `GG_VAPID_PRIVATE_KEY` environment variable.

The Web Push payload `services/notify` actually sends is JSON `{ "title", "body", "link", "tag" }` - `tag` is the `notifications` row's own id (so a repeat push for the same notification, if the sidecar's own retry ever produced one, replaces rather than stacks), `link` the same in-app path a notification's own `link` field carries. The portal's service worker is expected to open `link` on a click; this shape is fixed by that expectation, not by this backend's own convenience, so `services/notify` builds exactly this object and nothing else.

### Notifications

`GET /api/vault/me/notifications` (customer): `{ "items": [{ id, type, title, body, link, read_at, created }], "unread": <n> }`, newest first, capped at 50; `unread` is how many of the returned rows have no `read_at` yet. `POST /api/vault/me/notifications/:id/read` (customer own; 404 for anyone else's): sets `read_at` if not already set (idempotent), response `{ "notification": {...} }`. `type` stays the field name (not renamed to, say, `kind`) - the portal reads it as-is.

**A customer-facing `link` is always a portal path, never blank or a bare id**: `/account/quotes/<id>` for every quote event (`quote_message`, `quote_offered`, `quote_declined`, `quote_expired`, `quote_expiring`), `/account/wants` for both want-list events (`want_match`, `hold_released`), and `/account/notifications` for anything else - `lib/notify.js`'s own fallback, enforced at the one place every row is written rather than trusted to each call site, so a future event type can never ship with no link by omission. A staff-facing row (every `staffAll` call) carries its own `/counter/...` path instead and has no such fallback, since every one of this package's `staffAll` calls already sets one explicitly.

`lib/notify.js`'s `notify(app, { customer | staffAll, type, title, body, link?, email? })` is the one place a `notifications` row is written, for every event in this section (`staffAll` fans out to one row per active admin). It never sends push itself - every row's `pushed_at` starts empty, which is exactly what makes it eligible for `services/notify` to pick up; `email: true` sends inline, through the same `settings.email.test_mode`-honouring, plain-text, no-tracking path `lib/receipts.js`'s own email route uses (a from name/address from settings or PocketBase's own mail meta, a `Reply-To` when set, and a log line instead of a real send while `test_mode` is on - the default, so a fresh install cannot email anyone by accident). A customer with `notify_email: false` is treated as unreachable by mail for this call, not merely opted out of the log line; `services/notify` makes the equivalent check against `notify_push` before sending a push.

### Rate limits

This phase's migration adds three rules to PocketBase's own `app.settings().rateLimits` (a real, general platform setting - confirmed against this binary's `RateLimitsConfig`/`RateLimitRule`, so this is not a "say so if not" case): `customers:requestOTP` (`@guest`, 20 requests / 300 s - PLAN.md names this exact label), `GET /api/vault/estimate/search` and `GET /api/vault/estimate` (`@guest`, 60 requests / 60 s each). `rateLimits.enabled` is turned on for the whole instance to make these live; every other route matches none of the three rules and is unaffected, since PocketBase's limiter only ever throttles a request against a rule it actually matches.

## Phase 6: loyalty, rewards, perks, memberships and the display

The GG Guild engine: tiers and the rolling window that decides them, the welcome bonus, referrals, points expiry, the rewards catalogue and the vouchers redeeming one produces, the monthly perks wallet, paid memberships, the one admin route that moves points by hand, and the customer-facing display on the counter. Conventions are as above: money and points are integers, dates ISO 8601, errors `{ "message": "<a sentence>" }`. Token columns are the same three this document already uses: **staff** (`$apis.requireAuth("staff")`), **admin** (a staff token whose `role` is `admin`, checked with `lib/vaultutil.js`'s `requireAdmin`) and **customer** (`$apis.requireAuth("customers")`). Every write route here is audited with identifiers and counts only.

Nothing in `packages/shared`'s evaluator changed: `evaluateSalePoints`, `evaluateTradeInPoints`, `checkPointsRedemption`, `tierForPoints`, `pointsToNextTier` and `parseTierPerk` are untouched and stay the single source. Three pure helpers were added beside them in `packages/shared/src/loyalty.ts`, with Vitest tests, and the CommonJS copy under `pb/pb_hooks/lib/shared/` rebuilt from them:

- `tierWindowPoints(rows, now, windowMonths)`: the sum of `delta` over rows created within the last `windowMonths` calendar months, excluding rows whose reason is `redeem` or `expire`. Spending points, or letting them lapse, never costs a tier; a `refund_reverse` or a negative `adjust` does count against it, because each undoes something that earned it. `windowMonths` of 0 means all time. Dates are read in both ISO form and PocketBase's own stored form (`2026-09-20 12:00:00.000Z`, a space rather than a `T`), so the same row reads the same in the browser, in Vitest and in goja.
- `perkAllowance(tier, "free_event_entries" | "lounge_hours")`: that tier's monthly allowance, 0 when it has none.
- `resolveTier(tiers, windowPoints, activeMembershipTierId)`: whichever of the membership's tier and the earned tier sits higher up the ladder (`sort`), so a paid plan can only ever add to what somebody has earned and never take a tier off a long-standing customer whose points have carried them past it. A tie goes to the membership, which is the one they are paying for. No active membership, or one naming a tier that no longer exists, falls back to the earned tier rather than leaving the customer with none.

### Tiers, the welcome bonus, referrals and expiry

No new route: all four are hooks and crons in `pb_hooks/loyalty.pb.js` over `lib/tiers.js` and `lib/referrals.js`.

**Tier re-evaluation.** After every `points_ledger` write and after any `memberships` create, update or delete (a membership deleted outright through the collection API would otherwise leave a pinned tier with nothing pinning it), the server recomputes the customer's tier with `resolveTier` over `tierWindowPoints` (window from `loyalty_programme.tier_window_months`) and writes `customer_private.tier`. Every figure is read from `points_ledger` itself, never from the cached `points_balance`. A promotion writes one `notifications` row (type `tier_up`, title "You are now a Regular", link `/account/guild`) and emails when the customer has email on; a demotion is silent. "Promotion" means a higher `sort`, or the same `sort` and a higher `threshold_points`. Two promotions are deliberately not announced: **landing on the first rung**, which is every new customer and is what the welcome notification below is for, and **any change a merge causes**, which is bookkeeping rather than an achievement (`lib/tiers.js`'s `isJoiningTier`, and `recompute`'s `silent` option, which the merge passes). Nightly cron `tiers_recompute` (03:20) re-evaluates every customer so that points ageing out of the window take effect without a ledger write, which nothing else would produce; 03:20 rather than 03:30 so it does not run alongside `retention` and `quote_photos_retention`, which walk whole collections of their own.

**The welcome bonus.** When a `customers` row is created and `loyalty_programme.enabled` with `welcome_bonus > 0`, one `points_ledger` row with reason `welcome` is written for that amount, `ref` the customer's own id. Never twice for the same customer: the hook looks for an existing `welcome` row first, so a merge never adds another. A customer created **with an email address** also gets one notification for joining (type `welcome`, "Welcome to GG Guild", "100 points are on your card. Sign in to My Vault with this email address to see them.", link `/account`), emailed; one created at the counter without an address gets the bonus and no notification, since there is nowhere to read it and the row would only be noise in the list they find when they claim the account.

A merge brings the duplicate's own welcome bonus across with the rest of their ledger, which would leave the kept record holding two. Both rows stay, because `points_ledger` is append-only, and the merge writes an `adjust` row taking the second bonus back off plus a `notes` line, "Duplicate welcome bonus removed on merge". The merge's response reports it as `moved.welcome_bonus_removed`.

**Referrals.** Customers are created through the collection API rather than a `/api/vault/customers` route, so `referred_by` is handled by the `customers` create hook, which accepts either a customer **code** (`GGC7F3K2Q`, hyphenated or not - what staff and the portal actually send) or a record id. It refuses a code nobody holds with 400 "No customer has the code GGC-XXXXX. Check it with them.", and the customer's own id or code with 400 "A customer cannot refer themselves. Use the other person's code." On success it sets `customers.referred_by` to the resolved id and writes a `referrals` row, `pending`. When that customer's **first** completed trade-in or sale lands, one call from each of the two Phase 2 completion routes (`lib/referrals.js`'s `onFirstCompletion`, inside the route's own transaction, so the bonuses are atomic with the thing that earned them) flips the referral to `earned` with `earned_at` and writes two `points_ledger` rows with reason `referral`, `referral_bonus_referrer` to the referrer and `referral_bonus_referee` to the referee, each `ref` the referral's id. Both are notified (type `referral_earned`, link `/account/guild`); neither body names the other person. A second completion finds no pending referral and is a no-op. A referral that lands while the programme is switched off stays `pending` rather than being written off, so switching it back on honours it. `onFirstCompletion` also refuses outright to pay a row whose `referrer` and `referee` are the same customer, whatever wrote it: that is two bonuses to one person, and it is money, so it is guarded in the route that pays rather than trusted to the two places that stop such a row being written. `referred_by` can only be set at creation. A merge re-points both ends of a referral **except** a row whose two ends would become the same customer (somebody who signed up twice and gave their own first code the second time), which is deleted instead and reported as `moved.referrals_dropped`. An erasure leaves referral rows in place; they carry no personal data of their own.

**Points expiry.** Nightly cron `points_expire` (03:40). For every customer with a positive balance whose most recent `points_ledger` row with a positive `delta` is older than `loyalty_programme.expiry_months_inactive` months (0 turns expiry off entirely), one `expire` row is written for the whole balance and the customer is notified (type `points_expired`). Thirty days before that date, once, a `points_expiring` notification goes out ("Your 1,240 points expire on 20 Oct 2026. Any purchase keeps them.") with email. The warning is recorded on `customer_private.points_expiry_warned_at` (new field), so a thirty-night run-up sends one warning rather than thirty; the stamp is cleared the moment a new positive row lands, because that is exactly what resets the clock it was about.

### Rewards and vouchers (`pb_hooks/rewards.pb.js`, `lib/rewards.js`)

`loyalty_rewards` is admin-only through the collection API, so the portal reads the catalogue through a route rather than the collection, the same server-side window `GET /api/vault/config` already is for staff.

`GET /api/vault/rewards` (customer) returns `{ "rewards": [ { id, name, description_html, cost_points, type, value, image_url, remaining, per_customer_remaining, can_redeem, reason } ] }`, every `active` reward inside its `starts_at`/`ends_at` window, cheapest first. `remaining` is `stock_limit` minus every non-cancelled redemption, `null` when the reward has no limit; `per_customer_remaining` the same for this caller. `reason` is `"ok"`, `"insufficient"`, `"sold_out"`, `"limit_reached"`, `"not_yet"` or `"off"` (a reward that is live but has not opened yet is listed with `not_yet` rather than hidden, so a customer can see what is coming). `"off"` is `loyalty_programme.enabled` being false and beats every other reason: every row comes back `can_redeem: false` with that reason, and the portal shows the sentence the redeem route gives, "The rewards programme is switched off at the moment. Ask at the counter." A list offering rewards that all fail at the last step would be worse than saying so. `image_url` carries a file token minted from the caller's own auth record, the way quote photos do. The balance behind `insufficient` is summed from `points_ledger`, never the cached field.

`POST /api/vault/rewards/{id}/redeem` (customer) re-checks all of that against live rows inside one transaction and then, in it: creates the `reward_redemptions` row (`issued`, `points_spent`, `expires_at` now plus `settings.rewards.voucher_days`, default 90; the existing `redemptions.pb.js` hook assigns the sequential `GG-V-000001` number and the scannable `GGV…` code), writes `points_ledger` (`-cost_points`, reason `redeem`, `ref` the redemption id), and for a `store_credit` reward also writes `credit_ledger` (`+value`, reason `reward`, `ref` the voucher number) and marks the voucher `used` at once, because for that type the credit **is** the redemption and there is nothing to bring to the counter. Response `{ "voucher": { id, number, code, reward: { name, type, value }, status, expires_at, points_spent, created } }`. `points_spent` and `created` are carried beyond the shape the shared list named: every route in this section returns the same voucher object, and the portal lists it by date. `created` is the `reward_redemptions` row's own creation timestamp, and both it and `expires_at` go out as strict ISO 8601 with a `T` (`2026-09-20T21:42:00.123Z`), not PocketBase's stored form with a space, because a voucher is read by a customer's own browser and by the counter's, and both do nothing more than `new Date(voucher.expires_at)` with it (`lib/rewards.js`'s `isoDate`; V8 happens to parse the space form and other engines refuse it outright). This is the one place in this document where a stored date is normalised on the way out rather than passed through as PocketBase holds it. 422 with the reason as a sentence otherwise: "You need 500 points for this and have 320.", "That reward has run out. Pick another one from the list.", "You have had this reward as many times as the shop allows. Pick another one from the list.", "That reward opens on 1 Oct 2026. Come back then." The customer is notified (type `reward_issued`, link `/account/rewards`) and the redemption is audited as `reward_redeem` with the customer as `actor`.

`GET /api/vault/me/vouchers` (customer): `{ "vouchers": [...] }`, the same object as above including `created` and the same ISO dates, every status, newest first, 100.

`GET /api/vault/vouchers/{code}` (staff): `{ "voucher": { ...as above, including `created`, "customer": { id, code, name } } }` (the customer nested inside the voucher rather than beside it). 404 "No voucher with that code. Check it or scan it again." for an unknown code, in either the hyphened or bare form.

The Sell screen's own `reward_code` (`POST /api/vault/sales/complete`, Phase 2) resolves through the same `lib/rewards.js` lookup as the routes here, so a code typed in as it is printed (`GGV-ABC12`) finds the row a scanner's bare `GGVABC12` does. It keeps its own 422, "That reward code was not found. Check the voucher."

`POST /api/vault/vouchers/{code}/use` (staff) marks an `issued`, unexpired voucher of type `free_item`, `event_entry` or `custom` as `used` with `used_by`, notifies the customer (type `reward_used`) and audits it as `voucher_use`. 409 for a `money_off` voucher ("Use this one on the sale: scan it at Sell."), for a type the counter does not tick off at all, for anything not `issued` ("That voucher has already been used. Ask an admin if it should be reissued.") and for one past its `expires_at`.

`POST /api/vault/vouchers/{code}/cancel` (admin) turns an `issued` voucher `cancelled`, returns its `points_spent` as a `points_ledger` row with reason `adjust` (`ref` the redemption), and writes a `notes` row on the customer saying which voucher and how many points came back. Audited as `voucher_cancel`. 409 for a voucher in any other status.

Nightly cron `vouchers_expire` (03:50) marks every `issued` voucher past `expires_at` as `expired`. No points come back: cancelling is the deliberate way to hand them back, and an unused voucher is not a refund.

### Perks (`pb_hooks/perks.pb.js`, `lib/perks.js`)

`GET /api/vault/customers/{id}/perks` (staff) returns `{ "tier": { id, name } | null, "perks": [...] }` (the tier is carried alongside the wallet so the counter can label it without a second request). The wallet holds `{ type, value, allowed, used, period }` for each of the tier's counted perks, `free_event_entries` and `lounge_hours`, where `period` is `YYYY-MM` in Europe/London civil time (`lib/reports/dates.js`'s `toLondon`, the one place this codebase converts a timezone, since goja has no timezone database) and `used` comes from `perk_usage`; then the tier's informational perks as `{ type: "percent_off", value, scope }`, `{ type: "points_multiplier", value }`, `{ type: "priority_release_booking" }` and `{ type: "member_event_pricing" }`, which are applied where they are used (the Sell screen, the events diary) rather than counted here. A counted perk the tier does not carry is left out entirely rather than listed with an allowance of 0.

`POST /api/vault/customers/{id}/perks/use` (staff): `{ "type": "free_event_entries" | "lounge_hours", "count"?: 1 }` upserts the one `perk_usage` row for that customer, perk and period (the collection's unique index on the three), inside a transaction and re-checked in it, so two counters cannot both take the last free entry. Response `{ "perk": <the updated wallet entry> }`. 422 in two shapes, because they are two different pieces of news: "Only 1 lounge hour is left this month." when some of the allowance is left but fewer than were asked for, and "Both free entries this month are used. The next two come on 1 Oct." only when none is left at all. "Member does not include lounge hours. Check the tier's perks or pick another." when the tier has no such perk in the first place. 400 for a `type` that is not one of the two counted perks. Audited as `perk_use`.

### Memberships (`pb_hooks/memberships.pb.js`)

`POST /api/vault/memberships` (staff): `{ customer, tier, months: 1..24, price, payment_note? }`. The tier must have `paid_plan: true` (422 "Regular is earned with points, not bought. Pick a paid plan tier."), and the customer must not already have an `active` membership (409, naming the date the existing one runs to). Creates the row `active`, `started_at` now, `renews_at` now plus `months` calendar months; the tier is re-evaluated by the `memberships` hook rather than written here, so every route and cron reaches it by the same path. Notified (type `membership_started`), audited as `membership_start`. Response `{ "membership": { id, customer, tier, tier_name, status, started_at, renews_at, price } }`.

`POST /api/vault/memberships/{id}/renew` (staff): `{ months, price, payment_note? }` extends `renews_at` from the later of now and the current `renews_at`, so renewing early adds to what is left and renewing late does not backdate the new term into months already gone. A `lapsed` membership renews back to `active`; a `cancelled` one is 409 ("That membership was cancelled. Start a new one instead."). Because renewing makes a membership active again, the "one active membership per customer" rule the create route enforces is re-checked here as well, excluding this row: renewing a lapsed membership while another is live is 409, naming the live one's date. Audited as `membership_renew`.

`POST /api/vault/memberships/{id}/cancel` (staff): `cancelled`, tier re-evaluated, customer notified (type `membership_lapsed`), audited as `membership_cancel`.

Nightly cron `memberships_lapse` (04:00): every `active` membership past `renews_at` becomes `lapsed`, the tier is re-evaluated back to whatever the points earn, and the customer is notified ("Your Guild Pass ended on 20 Sep. Renew at the counter to keep its perks.").

### Adjustments

`POST /api/vault/loyalty/adjust` (admin, step-up as refunds use `lib/stepup.js`): `{ customer, delta: integer != 0, reason: string 5..500 }`. Writes a `points_ledger` row with reason `adjust`, a `notes` row on the customer carrying the reason, and an audit row (`points_adjust`, meta the customer, the delta and the resulting balance, never the reason text - `audit_log` is permanent and superuser-only). Response `{ "balance": <the live sum> }`. The balance is never allowed below zero: 422 "That would take them to -40 points. The most you can remove is 120.", checked once before the transaction for the fast refusal and again inside it against the live ledger, so two admins adjusting the same customer at once cannot both pass.

### Programme, rules, tiers and rewards editing

Still through the collection API under the existing admin-only rules. `audit.pb.js` audits an update to any of them and, since this phase, a create and a delete too, each row carrying the record's own `name` as its label: adding or removing a tier, a rule or a reward changes the programme's terms exactly as editing one does. The server now also validates on write (`lib/loyaltyconfig.js`, registered as `*Request` hooks so the refusal reaches the caller as its own sentence rather than PocketBase's generic "Failed to create record."):

- `loyalty_rules.conditions` must be an object whose keys are `games`, `kinds`, `minSpend` or `weekdays`, with the right types; an unknown key is refused by name ("Conditions has no \"kind\" setting. Use games, kinds, minSpend or weekdays."). The shared evaluator reads `conditions` as plain JSON, so a mistyped key would otherwise be silently ignored and quietly earn the wrong points. `value` must be above 0, and a `multiplier` or `day_of_week` value at most 10.
- `loyalty_tiers.perks` must parse entry by entry through the shared `parseTierPerk`; an entry it returns null for is refused by index ("Perk 1 is not a perk this app knows. ..."), which catches the pre-fix snake_case shapes that would otherwise disappear from a tier without a word. The two counted perks must also carry a whole, non-negative number: `lib/perks.js` counts entries and hours one at a time, and half a free entry is not something anybody can hand over. `parseTierPerk` itself is left alone, being the reader rather than the editor. `threshold_points` must be distinct among tiers that are not paid plans (two paid plans may share a threshold, since neither is reached by points at all). A tier that is a customer's current tier, or carries an active membership, cannot be deleted (409).
- `loyalty_rewards`: a `money_off` or `store_credit` reward needs a `value` above 0, and `ends_at` cannot precede `starts_at`. `loyalty_programme.points_per_pound_redemption` must be above 0, since both evaluators divide by it.

### The customer-facing display (`pb_hooks/display.pb.js`, `lib/display.js`)

New collection `display_state`, one row (the `singletons.pb.js` hook now guards it alongside `settings` and `loyalty_programme`): `mode` (`idle` | `sale` | `buy_in`), `payload` (json), `token`, `customer_accepted_at`, `updated_by`, `expires_at`. Staff may list, view and update it; create and delete are superuser-only. A customer token can do none of the four: the screen shows whoever is standing at the counter, which is nobody's own record.

Staff need list and view for the tablet to subscribe over realtime at all, and update is what the three routes below are for, which leaves a direct `PATCH` as a way straight past them. An `onRecordUpdateRequest` hook puts a write through the collection API through the same rules: the payload is re-run through the same strip and refused for the same reasons, and a request that tries to set `customer_accepted_at` or `token` is refused outright ("Only the customer's own Accept stamps the display. Use POST /api/vault/display/accept."). The three routes write through the hook app rather than as a request, so none of them is affected; `expires_at` is the one field on that row a client may still set directly.

`POST /api/vault/display` (staff): `{ mode, payload }` replaces the state, sets a fresh random `token`, clears `customer_accepted_at` and stamps `expires_at` fifteen minutes out. Response `{ "token", "mode", "expires_at" }` (the mode and expiry beyond the shared list's `{ token }`, so the caller can show its own countdown without reading the row back). The payload is **rebuilt field by field** from the shapes the contract names, so anything else is dropped rather than stored: for `sale` `{ lines: [{ title, detail, qty, unit_price, image_url? }], subtotal, discount, discount_label?, total, points_to_earn, customer_name? }`, for `buy_in` `{ lines: [{ title, detail, qty, offer_price, image_url? }], total_market, total_offer, payout_type, customer_name, credit_bonus_points? }`, for `idle` `{}`. On top of that, a payload carrying an identifier, an email or a phone number **anywhere in it, at any depth**, is refused outright with 400 ("The customer display never shows lines[0].item_id. Send only the lines, the totals and a first name.") rather than quietly stripped, so a client sending the wrong thing finds out. Audited as `display_publish`, meta the mode and the line count and nothing off the payload itself.

`POST /api/vault/display/accept` (staff, the tablet's own session): `{ token }` stamps `customer_accepted_at` when the token matches the live state and the mode is `buy_in`. 409 with "The display has moved on since that offer. Show the customer the offer again." for a token from an earlier publish, and "There is no offer on the display to accept." when the mode is not `buy_in`. A publish past its fifteen minutes is reset to `idle` first, in a transaction of its own, so the clear stands even though the accept is then refused. Audited as `display_accept`.

`POST /api/vault/display/clear` (staff): back to `idle`, keeping nothing of what was on the screen. Audited as `display_clear`.

The tablet at `/display` signs in as staff and subscribes to the `display_state` row over realtime; the buy-in wizard subscribes to the same row to learn about the accept. `settings.display` (`{ enabled, ticker, signup_url }`, seeded `{ false, "Game · Trade · Play", "/estimate" }`) and `settings.rewards` (`{ voucher_days: 90 }`) are both served to the counter by `GET /api/vault/config`, which already passes the whole settings record through minus its secrets.

### Portal

### Fix round (as reviewed)

A review of this package found ten items, one of them money, and they are all reflected above. The ones that changed behaviour rather than wording:

- **A merge could leave a customer referring themselves**, which the next sale would have paid both bonuses of to one person. The merge now deletes such a row instead of re-pointing it, and `onFirstCompletion` refuses one regardless of how it got there. This was the blocking finding.
- **`display_state` was writable straight through the collection API**, past the payload strip and past the token that decides whose Accept counts. An `onRecordUpdateRequest` hook closes both.
- **`GET /api/vault/me/export` had none of this phase's data in it.** Vouchers, memberships, this year's perk counts, the tier and window points and the customer's own referrals are in it now, with the other party of a referral named in no way at all.
- **Creating or deleting a tier, rule or reward was not audited**, only editing one.
- **A renewal could leave two active memberships** on one customer, so which one pinned the tier was a coin toss.
- **The Sell screen looked a voucher code up exactly** while every other route normalised it, so a code typed as printed failed there and nowhere else.
- **Every new customer was emailed "You are now a Member."** Joining the first tier is no longer announced; a single `welcome` notification naming the bonus goes to customers who have an email address, and nothing to those who do not.
- **`resolveTier` could lower a customer's tier**: buying a pass that sits below the tier their own points had earned replaced it. It now grants whichever sits higher.
- **A merge left the kept record holding two welcome bonuses**, and **the perks refusal claimed an allowance was spent when it was not**, and **the rewards list ignored the programme switch**, and **`tiers_recompute` ran alongside two other whole-collection passes at 03:30**. All four are fixed above.
- Smaller: a `memberships` delete now re-evaluates the tier, a counted perk has to be a whole number, the trade-in route guards its referral call on the customer id the way the sale route does, and an unused `require` is gone from `guild.pb.js`.

Section 24 grew by seventeen assertions for these, including a buy-in earning a referral, the three nightly crons changing nothing on a second run the same night, and the `buy_in` payload strip.

## Implementation notes (as built in Phase 6)

- **The welcome bonus and the referral row are written in the `customers` create hook after its single `e.next()`, not in an `onRecordAfterCreateSuccess` hook.** This one is worth knowing about beyond this package: a `points_ledger` row written from inside an after-create-success handler does **not** reliably reach the hooks that hang off a ledger write (`ledgers.pb.js`'s cached balances, `loyalty.pb.js`'s own tier re-evaluation). Confirmed against v0.40.4, repeatedly and intermittently: the row itself went in correctly, `balance_after` and all, and the customer was left with a cached `points_balance` of 0 and no tier until their next points row repaired both. Recomputing explicitly inside that handler did not fix it either, because a `runInTransaction` opened there is a separate transaction that cannot see the create's own uncommitted writes, and a recompute made on the visible side was then overwritten by the deferred one. Written after `e.next()` in the `*Request` hook (the shape `audit.pb.js` already uses for its own writes) the row is an ordinary ledger write and every hook fires exactly as it does for a correction typed in at the counter. The two writes are therefore outside the customer's own transaction, deliberately: a loyalty programme having a bad day can never stop a customer being created, the failure is logged, and the nightly `tiers_recompute` picks up anything that did not land.
- **A refusal thrown from a model-level `onRecordCreate` hook reaches the caller as PocketBase's own "Failed to create record."**, whatever message it carries. Every refusal in this package that a person is meant to read is therefore raised from a `*Request` hook: the referral code, and the four loyalty config validations.
- **`display_state`'s stale clear happens in its own transaction.** An accept that finds a publish older than fifteen minutes resets the row and then refuses; done in one transaction the refusal's own throw rolled the reset back with it, leaving the stale basket on screen.
- **`GET /api/vault/rewards` and `/api/vault/me/*` are the portal's only window onto `loyalty_rewards`, `perk_usage`, `memberships` and `referrals`**, all of which stay closed to a customer token through the collection API. `pb/scripts/check.sh` section 24 asserts a customer token lists none of them and cannot read or write `display_state`.
- **Response shapes carried beyond the shared list**, recorded here as the ones actually shipped: `GET /api/vault/customers/:id/perks` returns `{ tier, window_points, next, perks }` rather than a bare array (`tier` is the one `customer_private` holds; `window_points` and `next: { name, points_needed } | null` are computed live from the whole ledger, the way `/me/guild` computes them, so the counter's Guild block never adds a page of rows up for itself); `POST .../perks/use` returns `{ perk }`; `GET /api/vault/vouchers/:code` nests `customer` inside `voucher`; `POST /api/vault/display` returns `{ token, mode, expires_at }`; `POST /api/vault/display/accept` returns `{ accepted_at, mode }`; every voucher object carries `points_spent` and `created`, with both of its dates normalised to strict ISO 8601 (see the redeem route above; asked for by the portal review, and the counter's own `vouchers.ts` already parses `expires_at` with a bare `new Date`); the three membership routes return `{ membership }`. No shape was narrowed, and no route was moved or renamed.
- **`pb/scripts/check.sh` section 24** exercises all of the above with deterministic assertions and takes the script to 374 checks. Two of them need `points_ledger` rows that are genuinely months old (the rolling window's demotion, and the expiry cron), and PocketBase rewrites an autodate field on every write, so `created` cannot be set through the API at all, superuser included: the section starts a second, short-lived PocketBase on the same data directory whose entire hooks directory is one throwaway file doing the `UPDATE` through `$app.db()`. Nothing in `pb_hooks/` gains a test-only route, and the server under test keeps serving the repo's own hooks throughout.
- **The welcome bonus shifted six existing assertions in earlier sections of `check.sh`** (every customer now starts with 100 points, and a merged duplicate brings its own welcome row and the "you are now a Member" notification with it). Each was updated in place with a comment saying why, rather than the bonus being switched off for the test.
- **Dependencies**: none added. Every new file reuses helpers that already existed (`lib/vaultutil.js`, `lib/audit.js`, `lib/balances.js`, `lib/notify.js`, `lib/stepup.js`, `lib/counters.js`, `lib/quotes.js`'s date helpers, `lib/reports/{dates,query}.js`, `lib/shared/{loyalty,money,sku}.js`) plus the six new `lib/{tiers,rewards,perks,referrals,display,loyaltyconfig}.js` this package adds.

## Phase 7: the Solo card reader, reservation expiry, the price roll-up and the label queue

The polish round's own backend: a paired SumUp Solo taking the card payment from the Sell screen rather than staff typing the amount into the SumUp app, staff reservations that let go of themselves, a weekly thinning of the price history, and a print queue two devices can share. Conventions are as above: money is integer GBP pence, dates ISO 8601, errors `{ "message": "<a sentence>" }`. Token columns are the same: **staff**, **admin**, **customer**, plus one **public** route (the reader's own callback, which carries no token of ours at all).

### The Solo card reader (`pb_hooks/sumup_readers.pb.js`, `lib/readers.js`, `adapters/sumup.js`)

Nothing new to configure beyond the reader itself: the merchant API key at `settings.api_keys.sumup` and the merchant code at `settings.sumup.merchant_code` are Phase 4's, and `settings.sumup` gains `default_reader_id` and `default_reader_name` for the reader the counter uses by default (written by the pairing route, or by an admin through the settings PATCH, where both are checked to be text).

`GET /api/vault/sumup/readers` (staff): `{ "readers": [{ id, name, status, model }], "default_reader_id": "..." }` - SumUp's own live list. With no merchant code or key yet: 200 `{ "readers": [], "default_reader_id": "", "not_configured": true }`, never a 500, so the Settings screen can load and say so. A SumUp failure is 502 "SumUp did not answer. Try again in a moment."

`POST /api/vault/sumup/readers` (admin): `{ "pairing_code": "<8 or 9 characters from the reader's own Connections > API > Connect screen>", "name"?: "Counter Solo" }` -> `{ "reader": {...} }`. The first reader paired becomes the default. Audited as `sumup_reader_paired`. 422 "That pairing code was not accepted. Read the code off the reader again; it changes each time."

`DELETE /api/vault/sumup/readers/{id}` (admin): unpairs at SumUp, clears the default when it was this one, audits `sumup_reader_removed`, 204 with no body. A reader SumUp has already forgotten counts as unpaired rather than as a failure.

`POST /api/vault/sumup/checkouts` (staff): `{ "amount": <pence>, "sale_client_id": "<the Sell screen's own client_id>", "description"?: "GG-S-000456", "reader_id"?: "..." }` puts the amount on the reader. Response 200 `{ "checkout": { id, status, amount, description, sale_client_id, reader_id, reader_name, checkout_id, client_transaction_id, transaction_id, transaction_code, card_last4, error, paid_at, sale, created }, "reused": false }` - one shape, returned by this route, the poll and the cancel alike, and never carrying `callback_secret`.

**Idempotent per `sale_client_id`**, and not only while the payment is open: a till that asks twice (a retry, a double tap, the offline queue replaying) gets back the checkout already on the reader **or the one already paid for that basket that no sale has used yet**, with `reused: true`, rather than a second amount on the screen. A partial unique index on `(sale_client_id)` for `pending` rows makes that atomic, so two tills asking at the same moment cannot both put an amount on the reader; the one that loses the race has its own checkout stopped at the reader and is handed the winner.

Refusals: 422 "SumUp is not set up. Add the merchant code and API key under Settings."; 422 "No card reader is paired. Pair one under Settings."; 400 for an amount that is not a whole number of pence above zero (`"42.00"` is refused rather than read as 42p) and for a missing `sale_client_id`; 422 "That reader is no longer paired. Pair it again under Settings." (SumUp 404); 422 "The reader is offline. Check it is on and connected, then try again." (SumUp 422); **409 "The reader is busy with another payment. Finish or cancel that one first." (SumUp 409, a reader already taking somebody else's payment)**; 422 "The application URL is not set, so the reader cannot report back. Set it in the PocketBase settings." when `app.settings().meta.appURL` is empty or is not https (127.0.0.1 and localhost are allowed, for development); and **502 "SumUp did not give that payment a reference, so it could not be tracked. Check the reader, and the SumUp app, before taking it again." when SumUp answers without a `client_transaction_id`** - there would be nothing to verify the payment by afterwards, so the amount is taken back off the reader and no row is written. Every path that fails after the amount is live on the reader terminates it, so a failure never leaves money on the Solo with nothing tracking it. Rate limited to 30 a minute per authenticated caller.

`POST /api/vault/sumup/callback/{token}` (public, rate limited to 60 a minute): the reader's own result. An unknown token is a bare **404 with no body at all** - no hint that a token exists or does not. Once the token matches, the answer is always 200 `{}`, whatever the outcome. The body is read defensively and only for `payload.failure_reason`; what actually happened is read from `GET /v2.1/merchants/{code}/transactions?client_transaction_id=`, the merchant's own record: `SUCCESSFUL` for the amount asked for -> `paid` with `transaction_id`, `transaction_code`, `card_last4` and `paid_at`, audited `sumup_checkout_paid` with the amount and the code; `FAILED` or `CANCELLED` -> `failed` with the callback's own reason, or "Declined"; `PENDING`, or a transaction SumUp does not know yet -> left `pending`. A row already in a final state is never changed, however many callbacks arrive.

A `SUCCESSFUL` transaction **for a different amount** is `failed`, not paid: "The reader took a different amount (£47.00). Refund it from the SumUp app and take the payment again.", audited `sumup_checkout_amount_mismatch`. The comparison is integer pence both sides, SumUp's own decimal parsed through the shared `parseDecimalToMinor`, never a float, and **in one currency**: a transaction whose `currency` is not GBP is `failed` too, "The reader took EUR, not pounds. Check the payment in the SumUp app before taking it again."

**A transaction that names a different payment is no answer at all.** The lookup is filtered by `client_transaction_id`, and both the adapter and the decision check that what came back carries the reference that was asked about (a list shape is searched for it rather than read off the front). A filter SumUp stopped honouring would otherwise hand back the merchant's newest transaction, and any checkout whose amount happened to match it would be marked paid on somebody else's payment.

**A payment that arrives after the row was closed leaves the row closed.** `cancelled` and `expired` are final, because the counter has already been told the sale was not paid for, and re-opening one would contradict that. One `sumup_checkout_late_payment` audit row per checkout records that SumUp reports the money as taken; the hourly pull then shows that transaction on the Cash screen with no sale against it, which is where a refund gets decided.

`GET /api/vault/sumup/checkouts/{id}` (staff): `{ "checkout": {...} }`. While it is still `pending` and more than five seconds old, SumUp is asked first (the transactions lookup, then the reader's own checkout status if that knows nothing yet) and the same transitions are applied, so a callback lost on the way never strands a sale. The counter polls this every three seconds while it waits, on top of its realtime subscription; one checkout is asked about at most once every ten seconds however often it is polled, so an unattended payment costs SumUp tens of calls rather than hundreds. A callback, a cancel and the expiry cron always ask.

`POST /api/vault/sumup/checkouts/{id}/cancel` (staff, the till that started it or an admin): stops the reader, then checks. Terminate is reader-scoped at SumUp, not checkout-scoped, so the reader is only reached for when this checkout is still the one on it: a row with a newer `pending` checkout behind it on the same reader, or one SumUp already reports as finished, is closed without touching the reader, so tidying up a stale payment can never kill the live one beside it. If the customer paid in the meantime the row becomes `paid` and the response is **409** `{ "message": "The customer already paid. Complete the sale.", "checkout": {...} }` - the checkout comes back with the refusal, so the Sell screen can carry straight on to completing the sale. Otherwise `cancelled`, audited `sumup_checkout_cancelled`. 403 for another till's payment.

**Which payment paid for a sale is decided by the completion route alone.** `sales.updateRule` now refuses a staff `PATCH` that carries `sumup_checkout` at all (the same `@request.body.<field>:isset = false` shape `sumup_transactions` already uses; an admin is unrestricted, and every other field of a sale is still editable as before), because a direct write would assert the amount match, the paid status and the "nothing else has used it" check without performing any of them.

`POST /api/vault/sales/complete` (Phase 2) accepts **`sumup_checkout`**: the checkout must be `paid`, unused, and for exactly the card part of the sale (`payment_split.sumup_card`, or `total` when `payment` is `sumup_card`). On success `sales.sumup_ref` is the reader's own `transaction_code`, `sales.sumup_checkout` and `sumup_checkouts.sale` point at each other, and all of it is inside the sale's own transaction. Refusals: 422 "That card payment is pending, not paid. Take the payment on the reader before completing the sale."; 422 "That card payment was not found. Take the payment on the reader again."; **409** "That card payment has already been used on sale GG-S-000456." (`sales.sumup_checkout` is uniquely indexed, so this holds however many times a request is replayed); 422 "The reader took £42.00 but the card part of this sale is £40.00. Adjust the split or refund the difference from the SumUp app." A replayed `client_id` still returns the first sale, exactly as before.

Cron `checkouts_expire` (every five minutes): a `pending` checkout older than fifteen minutes is asked about once more and then `expired` ("The reader did not report a payment within 15 minutes."), or `paid` if the money did arrive. Idempotent.

The hourly SumUp pull (`lib/sumup.js`) now matches a fetched transaction to a sale by `sumup_checkouts.transaction_id` **first**, before the SKU rule and the amount-and-time rule: that is SumUp's own id for a payment this app started and watched, where the other two are inferences.

**Refunds stay manual through the SumUp app.** Nothing here refunds a card payment, and the refund route's own copy already says so.

### Collection `sumup_checkouts`

Staff may list and view. Create, update and delete are all `null`: the routes above run as `$app` and bypass collection rules, so nothing a till sends can mark a payment paid. Fields: `staff`, `sale_client_id` (required, indexed), `amount` (pence), `description`, `reader_id`, `reader_name`, `checkout_id`, `client_transaction_id` (uniquely indexed), `status` (`pending` | `paid` | `failed` | `cancelled` | `expired`), `transaction_id`, `transaction_code`, `card_last4`, `error`, `callback_secret` (the sha256 of the token in the reader's `return_url`, never the token), `paid_at`, `sale`, autodates. `sales` gains `sumup_checkout` (relation, uniquely indexed where set).

### Reservation expiry (`pb_hooks/reservations.pb.js`, `lib/reservations.js`)

Cron `reservations_expire` (`5-59/15 * * * *`, offset from `holds_release`): every `items` row that is `reserved` with a `reserved_until` in the past and **no** `matched` `want_list` row pointing at it - the exact inverse of the set `lib/wants.js`'s `releaseExpiredHolds` takes - goes back to `in_stock` with `reserved_for` and `reserved_until` cleared, one `notes` row on the item ("Hold for Sam Bell ended 20 Sep 2026; back on the shelf.") and one `audit_log` row `reservation_expired` carrying the sku, the customer and the until date. **No customer notification**: this was a promise a person made across the counter, not one the system made. A reservation with an empty `reserved_until` never expires; each item is released in its own transaction and a second run does nothing.

### Price snapshot roll-up (`pb_hooks/snapshots.pb.js`, `lib/snapshots.js`)

Cron `snapshots_rollup` (`30 2 * * 0`, half an hour clear of the weekly `prices` set sync at 03:00) and `POST /api/vault/prices/rollup` (admin) both call `rollup(app, now)` and return `{ "scanned": <n>, "kept": <n>, "deleted": <n>, "capped": false }` - how many rows older than 90 days were looked at, how many are left, how many went, and whether the run stopped at its own row cap. Past 90 days one row per (card or retro title, finish, source, ISO week) is kept, the newest in the week; nothing inside the 90 days is touched at all, and the newest row of any (target, finish, source) is never deleted whatever its age, so a card priced once a year ago still has its one price.

It **streams**: a page of rows at a time, keyset paged on `(fetched_at, id)`, keeping only one row per target per week in hand, and deleting in batches of 500 as each batch fills rather than at the end. A run stops after 50,000 rows and reports `capped: true`, so the first pass on a database that has never been thinned converges over a few weekly runs instead of holding the whole process, and an admin pressing the button never waits on a million rows. The route is audited as `snapshots_rollup` with the counts and the cap.

### Labels: bulk reprint and the cross-device queue (`pb_hooks/labels.pb.js`, `lib/labels.js`)

`label_jobs.status` gains `printing` and `failed` beside `queued`, `printed` and `cancelled`, and the collection gains `printer` (the device that claimed the job), `claimed_at`, `attempts` and `error`. It stays staff-only, and the print page at `/labels/print` still lists jobs (`expand=item,template`) and marks them printed through the collection API exactly as before.

`POST /api/vault/labels/queue` (staff): `{ "items"?: [ids], "trade_in"?: id, "acquired_from"?: "YYYY-MM-DD", "acquired_to"?: "YYYY-MM-DD", "location"?: id, "kind"?: kind, "game"?: id, "template"?: "<template key>", "copies"?: 1, "include_queued"?: false }` -> `{ "queued": <n>, "skipped": <n>, "job_ids": [...] }`. At least one selector is required (400 "Pick what to print: the items, a buy-in, a date range, a location, a kind or a game."). Only stock the shop still holds is ever labelled (`in_stock`, `reserved`, `listed_ebay`); a `trade_in` selector takes every item that buy-in's lines created. `copies` is a whole number from 1 to 20 (400 "Copies has to be a whole number between 1 and 20."). Over 500 **labels**, which is the item count times `copies`: 400 "That is 812 labels. Narrow the range to 500 or fewer.", and nothing is queued; an `items` list longer than 500 is refused the same way before a filter is built out of it. An item that already has a `queued` or `printing` job is skipped unless `include_queued` is true. With no `template`, each item gets the size the buy-in wizard would have given it (top loader for singles and graded, boxed retro for retro and for boxed sealed, the sleeve for everything smaller), falling back to `settings.label_default_template`. Audited as `labels_queued` with the counts, the selector and at most twenty job ids.

`POST /api/vault/labels/claim` (staff): `{ "printer": "<device name, required, <= 60>", "limit"?: 10, "templates"?: ["<keys>"] }` -> `{ "jobs": [ { id, status, copies, attempts, printer, claimed_at, printed_at, error, template: { id, key, width_mm, height_mm, dpi }, item: { id, sku, title, set_code, number, finish, condition, price, kind, game_key, qr_text } } ] }`. Up to `limit` (default 10, at most 50) of the oldest `queued` jobs flip to `printing` with the device's name and the time, inside one transaction that re-reads each row's status first, so two devices claiming at the same moment take two different batches. `qr_text` is the same text the print page's own `labelLayout` puts in the QR today: the item's SKU. Nothing is returned that the print page does not already show.

`POST /api/vault/labels/{id}/printed` (staff): a **`printing`** job -> `printed` with `printed_at`. `{ "job": {...} }`, the same job shape as a claim. 409 for anything else, including a job that has gone back into the queue: "That label went back in the queue, so another device may have printed it. Check the label before printing it again." - a device printing a label it no longer holds is a duplicate somebody has to know about, not something to accept quietly.

**Each `/printed` call is also the claim's heartbeat.** A device prints its batch one label at a time and reports each one, so every report pushes the `claimed_at` of the rest of that device's batch forward and `labels_unstick` leaves it alone. Nothing new for a client to call, and no extra write in the normal case: only a claim already older than half the stuck window is touched.

`POST /api/vault/labels/{id}/failed` (staff): `{ "error": "Printer out of labels" }` -> `attempts + 1`, the reason kept, and back to `queued` while `attempts < 3`, `failed` at the third. `{ "job": {...} }`.

`POST /api/vault/labels/{id}/requeue` (staff): a `failed` or `cancelled` job -> `queued`, attempts and error cleared. `{ "job": {...} }`. 409 from any other status.

Cron `labels_unstick` (every five minutes): a job still `printing` ten minutes after it was claimed, with no `/printed` call from its device in that time, goes back to `queued` with `attempts + 1` and "The printer stopped answering", so a label a device died holding is not lost. At the third strike it becomes `failed` instead, the same rule the failed route follows, rather than cycling round the queue for ever with a counter climbing past it; `POST /api/vault/labels/{id}/requeue` is how it comes back. Idempotent - a requeued job carries no `claimed_at`.

### Implementation notes (as built in Phase 7)

- **A callback is never believed on its own.** The token in `return_url` proves which checkout SumUp is talking about and nothing else; every transition comes from the transactions lookup. Only the sha256 of that token is stored (`callback_secret`), because `sumup_checkouts` is readable by every staff member and a stored token would be a way to post a payment that never happened.
- **The reader's own checkout status can only ever fail a payment, never pay one.** It carries no amount and no transaction code, so believing a `SUCCESSFUL` there would mean marking a sale paid without having seen what the merchant account actually took. The poll uses it as a fallback for a definite negative only; a real payment always comes from the transactions lookup.
- **An amount SumUp answers with that cannot be parsed at all** fails the checkout with "The reader's amount could not be read. Check the payment in the SumUp app before taking it again." rather than leaving it open or guessing zero - the contract names the mismatch case but not this one, and this is the reading that never claims money moved when the server cannot tell.
- **A `REFUNDED` transaction fails the checkout** ("That payment was refunded on the reader. Take the payment again.") rather than leaving it pending: money that arrived and went straight back out is not a payment a sale can be completed against.
- **`POST .../cancel` answers 409 with a body**, `{ message, checkout }`, rather than a bare error: the checkout in that body is the one that just turned out to be `paid`, which is exactly what the Sell screen needs to carry on and complete the sale.
- **A second sale on one card payment is 409, not 422** - it is the same "somebody already did this" shape as a trade-in completed twice - and the message names the sale that has the payment.
- **The create route is not audited**; the `sumup_checkouts` row is itself the record of the attempt, and the three transitions that matter (`paid`, a mismatched amount, a cancel) each write their own audit row. `sumup_checkout_failed`, `sumup_checkout_expired`, `sumup_checkout_amount_unreadable` and `sumup_checkout_late_payment` are written too, for the same reason: every way a payment ends is on the record, and only the attempt itself is not.
- **`reused: true`** on a repeated checkout request is beyond the contract's own shape list, so the counter can tell "this is the amount already on the reader" from "this is a new one" without comparing ids.
- **The roll-up's "never delete the last price" rule is belt and braces.** Rows arrive oldest first, so a row is only ever deleted at the moment a later row of the same target and week replaces it, which means every target keeps its newest row whatever its age; the check is written out anyway, because a price quietly disappearing is not something anybody would notice until they needed it.
- **The label queue's `skipped` counts items left alone because they already have a `queued` or `printing` job.** An item the selector matched but the shop no longer holds (sold, returned, written off) never enters the set at all and is not counted anywhere: a label for something that has left the building is not a job anybody wanted.
- **`labels_unstick` counts an abandoned claim as an attempt and stops at the third**, the same rule `POST .../failed` follows, rather than cycling a job round the queue for ever behind a printer that is never coming back. The job is `failed`, which is visible on the queue screen, and `POST .../requeue` is how it comes back. Its claim is renewed by each `/printed` call, so a device genuinely working through a long batch never reaches the cron at all.
- **`POST /api/vault/labels/{id}/printed` does not touch `items.label_printed_at`.** The print page does not set it today either; nothing reads it, and a reprint is not new information about the item. It does refuse a job that is not `printing`, which is a change from this section's first draft: a device reporting a label it no longer holds has printed a duplicate, and saying so is the only way anybody finds out.
- **A caller holding a valid callback token can choose the `error` sentence staff read** on a payment SumUp itself reports as failed, bounded to 300 characters. Known and left as it is: the token is single-purpose, the text can change no status and no amount, and the alternative is a generic message that tells staff less than the reader's own reason does.
- **The rate limits are keyed on the caller's address, not on the token.** PocketBase's `audience` decides which callers a rule applies to, not what the count is kept per (confirmed against this binary: two different staff tokens from one address share one bucket), so "30 a minute" is 30 a minute from the shop, which behind one Caddy IP is what this deploy wants anyway.
- **Two rate limit rules were appended to Phase 5's own four**, not substituted for them: `POST /api/vault/sumup/checkouts` at 30 a minute for authenticated callers, and the prefix `POST /api/vault/sumup/callback/` at 60 a minute for everyone (PocketBase matches a label ending in `/` as a path prefix, which is what a token in the path needs). `down()` removes exactly those two and leaves the others alone.
- **`pb/scripts/check.sh` section 25** exercises all of the above and, with the fix round below, takes the script to 450 checks. Like section 24 it starts a second, short-lived PocketBase on the same data directory whose entire hooks directory is one throwaway file: `sumup_checkouts.created` is an autodate the API cannot set (the expiry cron measures from it), and `callback_secret` holds the sha256 of a token the server generates and never hands out, so posting a callback the way SumUp does means putting a known token's own hash there first. Nothing in `pb_hooks/` gains a test-only route. The SumUp Readers API itself is answered by `pb_hooks/adapters/fixture_transport.js`, which derives its answer from the request: the outcome the test wants (paid, pending, failed, a mismatched amount) travels in the checkout's own `description` and comes back inside the `client_transaction_id`, which is the id the transactions lookup is then asked about, so a poll, a callback and the cron all get the same answer with nothing remembered between calls.
- **Dependencies**: none added. Every new file reuses helpers that already existed (`lib/vaultutil.js`, `lib/audit.js`, `lib/csv.js`, `lib/quotes.js`, `lib/shared/money.js`, `adapters/http.js`) plus the new `lib/{readers,reservations,snapshots,labels}.js` this package adds. `packages/shared` is untouched: `parseDecimalToMinor` and `formatGBP` already cover every figure here.

### Fix round (as reviewed)

A high-effort review of this package found two blocking items, seven to fix, twelve minor ones and eleven gaps in `pb/scripts/check.sh`. Everything above already reflects them; these are the ones that changed behaviour rather than wording.

- **A checkout SumUp gives no reference to is refused, not stored.** `client_transaction_id` is what every later verification looks the payment up by, so a row without one could only ever expire while the customer had been charged. The reader is terminated, the call answers 502 in words, and the unique index on that column is partial (`WHERE client_transaction_id != ''`) so a second such row could never collide at the save either. Every failure after the amount is live on the reader now terminates it.
- **The transactions lookup checks that the transaction it got back is the one it asked for.** That one call is the whole trust model; without the check, a filter SumUp stopped honouring would have marked checkouts paid on other people's payments.
- **The amount comparison is in GBP or it is not a payment**, and **a cancel that finds the payment already made answers 409 with the row**, whichever of the two windows the callback landed in.
- **Cancel only reaches for the reader when this checkout is still the one on it**, so tidying up a stale payment cannot kill the live one beside it, and **SumUp's 409 is "the reader is busy", not "the reader is offline"**.
- **Idempotency is a database guarantee, not a read-then-write**, and it now covers a payment already taken and unused for that basket.
- **The roll-up streams** rather than reading every old row into memory.
- **A device keeps its claim while it is printing**, `/printed` refuses a job the device no longer holds, and an abandoned claim stops at the third strike.
- **Only the completion route can point a sale at a payment** (`sales.updateRule`).
- **A payment that lands after a cancel or an expiry is recorded** (`sumup_checkout_late_payment`) instead of passing unnoticed.
- **The poll asks SumUp at most once every ten seconds per checkout**, and **a settings save that does not mention the reader no longer unpairs it**.

`pb/scripts/check.sh` section 25 grew by twenty-two assertions for these and for the eleven gaps the review listed, including both rate limits bursted against the rules the migration itself installed, two tills asking for one basket at once, two tills completing one sale at once, two devices claiming labels at once, the reader-status fallback, a refunded and an unreadable amount, a reservation with no end date, the roll-up splitting a group by finish, by source and on a retro title, and a late payment on a cancelled and on an expired row.
